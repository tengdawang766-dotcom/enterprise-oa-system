# 企业 OA 协同办公系统 V1.0

## 前端模块划分与目录规划

------

# 1. 设计原则

本项目建议采用：

> **业务模块优先 + 少量应用级公共基础设施 + 页面局部状态优先**

而不是传统的：

```
pages/
components/
api/
types/
```

把所有业务混在一起。

原因是 OA V1.0 已经具有非常明确的业务边界：认证、员工、部门、通讯录、公告、请假、审批、概览等。需求本身也明确将账号、部门负责人、公告、请假审批作为相互独立但存在协作关系的业务。fileciteturn2file0L19-L29

因此采用：

```
features/
  auth/
  profile/
  employees/
  departments/
  directory/
  announcements/
  leaves/
  approvals/
  dashboard/
```

每个模块自己管理页面、私有组件、API、DTO、Hooks 和必要工具。

公共代码只保留真正跨业务模块复用的东西，例如：

- Axios 实例；
- Router；
- Layout；
- 当前用户状态；
- 权限守卫；
- 通用加载/错误/空状态；
- 通用分页协议；
- 日期格式化；
- 全局主题。

特别注意：

**部门负责人绝对不能建成第三种前端角色。**

系统基础角色只有：

```
ADMIN
EMPLOYEE
```

负责人是 EMPLOYEE 当前承担的组织职责。数据库设计也已经明确 `users.role` 不保存 `DEPARTMENT_MANAGER`，负责人身份来源于当前部门负责人关系。fileciteturn1file4L341-L349

因此不应该出现：

```
role === 'DEPARTMENT_MANAGER'
```

这样的判断。

前端应采用类似概念：

```
role = EMPLOYEE
isDepartmentManager = true
```

但字段具体叫什么，以最终 REST API 为准。

# 3. 目录职责说明

## `app/`

负责整个 React 应用的“运行骨架”。

包括：

- Router；
- Route Guard；
- Layout；
- Provider；
- 应用启动初始化。

可以依赖：

```
stores/
shared/
features/
```

不应该放：

- 员工 CRUD；
- 公告请求；
- 请假计算；
- 部门负责人业务规则。

------

## `features/`

整个项目最重要的目录。

一个业务模块对应一个 feature。

例如：

```
features/leaves
```

只处理“我的请假”业务。

而：

```
features/approvals
```

处理“作为审批人处理别人申请”的业务。

虽然底层都是 `leave_requests`，但前端业务视角不同，不建议硬塞成一个巨大模块。

------

## `shared/`

只放真正跨模块使用的公共能力。

例如：

```
LoadingState
ErrorState
PageHeader
httpClient
ApiError
分页类型
日期格式化
```

不应该放：

```
EmployeeFormModal
LeaveApplicationModal
DepartmentManagerModal
```

这种具有明确业务语义的东西。

------

## `stores/`

只存全局共享状态。

V1.0 建议只有一个核心：

```
auth.store.ts
```

不要建立：

```
employee.store.ts
department.store.ts
announcement.store.ts
leave.store.ts
approval.store.ts
```

这些列表不是跨页面长期共享状态。

------

## `styles/`

负责：

- Ant Design Theme；
- 全局样式；
- CSS Variables；
- 页面基础背景、字体等。

不要把某个业务页面的大量私有样式放这里。

# 5. 路由与权限规划

建议统一使用 `/app` 作为登录后的应用区域。

| `/change-password`         | 修改密码     | 是    | ADMIN / EMPLOYEE  | 否                     | **允许**     |
| `/app/overview`            | 工作概览     | 是    | ADMIN / EMPLOYEE  | 否                     | 禁止         |
| `/app/profile`             | 个人资料     | 是    | ADMIN / EMPLOYEE  | 否                     | 禁止         |
| `/app/admin/employees`     | 员工管理     | 是    | ADMIN             | 否                     | 禁止         |
| `/app/admin/departments`   | 部门管理     | 是    | ADMIN             | 否                     | 禁止         |
| `/app/directory`           | 通讯录       | 是    | EMPLOYEE          | 否                     | 禁止         |
| `/app/announcements`       | 员工公告列表 | 是    | EMPLOYEE          | 否                     | 禁止         |
| `/app/announcements/:id`   | 公告详情     | 是    | EMPLOYEE / ADMIN* | 否                     | 禁止         |
| `/app/admin/announcements` | 公告管理     | 是    | ADMIN             | 否                     | 禁止         |
| `/app/leaves`              | 我的请假     | 是    | EMPLOYEE          | 否                     | 禁止         |

| `*`                        | 404          | 否/是 | ALL               | 否                     | 可           |

### `/app/directory`

管理员是否能访问通讯录目前不能自行决定。

API 输入文档明确把：

> 管理员是否允许使用通讯录

列为待产品确认。fileciteturn2file4L341-L357

页面需求当前则只明确员工和负责人可使用通讯录。fileciteturn2file7L668-L676

所以 V1.0 当前先标：

```
ADMIN：待确认
EMPLOYEE：允许
```

## 审批工作台是一个特殊点

不能简单写：

```
isManager === true
```

才能进 `/app/approvals`。

因为需求明确：

> 负责人卸任后，仍可以查看自己以前处理过的审批记录。fileciteturn2file14L1217-L1223

也就是说存在：

```
现在不是负责人
但以前做过审批人
```

的 EMPLOYEE。

因此审批工作台真正的访问条件应接近：

```
当前负责人
OR
存在本人历史审批记录
```

而不是：

```
当前负责人
```

这一点需要最终 API 给前端足够的信息。

这是目前一个重要的 API 契约待确认项。

所以不要只隐藏 Sidebar。

# 6. Zustand 状态管理方案

建议 `auth.store.ts` 只管理认证上下文。

## Store 概念字段

```
currentUser

authInitialized

authenticationStatus
  unknown
  authenticated
  guest
```

当前用户 DTO 至少需要提供能够判断：

```
id
username
name
role
status
department
mustChangePassword
是否当前负责人
```

具体字段名等最终 API。

API 输入已经明确指出，对 `EMPLOYEE`，当前用户数据必须让前端能够判断其当前是否承担负责人职责。fileciteturn2file8L770-L790

### 建议不要单独重复保存

```
isAdmin
isEmployee
mustChangePassword
isManager
```

四套可能互相不同步的状态。

如果 API DTO 已经包含：

```
role
mustChangePassword
managerCapability
```

应该尽量从 `currentUser` 派生。

------

## Store Actions

概念上需要：

```
initializeAuth()

refreshCurrentUser()
markAuthInitialized()
```

不需要现在写代码。

# 不放 Store 的数据

明确不长期放：

```
员工列表
部门列表
通讯录
公告列表
公告阅读记录
我的请假
审批待办
审批历史
Dashboard 数据
普通表单
分页条件
```

原因：

这些是服务端业务状态。

业务操作后重新请求即可。

API 输入也明确说明 V1.0 不需要实时推送，相关状态在操作或刷新后反映最新结果即可。fileciteturn1file11L818-L836

# 应用启动恢复登录

由于 JWT 在 HttpOnly Cookie：

```
浏览器刷新
↓
JS 无法读取 JWT
↓
AuthBootstrap
↓
调用“当前用户接口”
↓
浏览器自动携带 Cookie
↓
后端校验 JWT
↓
返回 CurrentUser
↓
写入 Zustand
↓
authInitialized = true
```

严禁：

```
localStorage.getItem('token')
decodeJwt()
document.cookie
```

来恢复用户。

------

# 登录成功

建议：

```
提交账号密码
↓
后端设置 HttpOnly Cookie
↓
登录成功
↓
获取/接收 CurrentUser
↓
setCurrentUser()
↓
mustChangePassword?
├─ true → /change-password
└─ false → /app/overview
```

------

# 修改密码成功

需求明确修改密码后旧登录状态失效。fileciteturn2file3L247-L255

所以：

```
修改成功
↓
clearCurrentUser()
↓
提示密码修改成功，请重新登录
↓
/login
```

不要：

```
修改成功 → Dashboard
```

------

# 退出

```
调用 logout API
↓
后端清除/失效 Cookie 登录状态
↓
clearCurrentUser()
↓
/login
```

# 7. Axios 与错误处理

建议：

```
shared/api/http-client.ts
```

创建唯一 Axios 实例。

概念配置：

```
baseURL = '/api/v1'
withCredentials = true
```

这样 JWT Cookie 自动由浏览器发送。

前端不读取 JWT。

employees.api.ts
```

职责类似：

```
queryEmployees()
createEmployee()
updateEmployee()
resetEmployeePassword()
disableEmployee()
```

这里表达的是前端业务函数名称。

**不是现在确定后端 URL。**

------

### Axios Instance

负责：

- `/api/v1`；
- Cookie；
- HTTP 层异常标准化；
- 登录状态失效处理；
- 网络异常标准化。

不负责：

```
“该员工存在待审批申请，所以不能停用”
```

这种业务解释。

------

# 登录失效处理

特别需要防止：

```
页面加载 5 个请求
↓
Cookie 已过期
↓
全部失败
↓
弹 5 次“登录失效”
↓
跳 5 次 /login
```

建议设计全局 authentication expiration gate：

```
authExpiredHandling = false
```

第一次发现明确的登录失效：

```
false → true
↓
clearCurrentUser()
↓
只提示一次
↓
跳 /login
```

后面的认证失败请求直接结束，不再重复提示。

完成登录后重置。

------

# 注意：不能把所有 401 都机械处理

因为登录页错误：

```
账号错误
密码错误
```

本身也可能使用 HTTP 401。

所以最终必须结合：

```
HTTP Status
+
后端业务 error code
+
当前请求是否认证业务
```

判断是不是 Session 失效。

而目前上传的 API 输入文档没有定义 HTTP Status 和业务错误码。

因此这部分必须等待最终 REST API 契约。

------

# 业务错误

例如：

```
EMPLOYEE_HAS_PENDING_LEAVE
MANAGER_HAS_PENDING_APPROVAL
DEPARTMENT_HAS_RELATIONS
ANNOUNCEMENT_STATE_CHANGED
LEAVE_ALREADY_PROCESSED
```

这些错误是否存在、名字叫什么，都不能由前端现在编。

前端只需要架构支持：

```
ApiError
├─ status
├─ code
├─ message
└─ fieldErrors?
```

最终字段以 API 设计为准。

业务错误应返回给页面。

例如员工停用失败：

```
employees.api
↓
后端返回具体限制原因
↓
EmployeeManagementPage
↓
Modal / message 展示具体原因
```

需求明确组织调整受限时不能只显示“操作失败”，必须说明具体原因。fileciteturn1file1L98-L102

------

# 网络结果不确定

这一点非常重要。

不能：

```
POST
↓
网络超时
↓
前端提示“创建成功”
```

也不要自行假定：

```
超时 = 后端一定没执行
```

因为可能：

```
数据库已经提交
↓
响应返回途中网络断开
```

页面应：

```
提示：
“请求结果暂无法确认，请刷新或查询最新状态”
```

然后重新查询服务器。

页面需求同样明确要求网络结果不确定时不能直接显示成功。fileciteturn2file11L979-L985

## API DTO 类型

原则：

> 前端 API 类型描述的是 HTTP 契约，不是 MySQL Table。

例如数据库存在：

```
password_hash
token_version
state_version
```

不代表：

```
interface User {
  passwordHash: string
  tokenVersion: number
}
```

必须出现在前端。

数据库甚至明确包含 `password_hash`、`token_version` 等服务端数据。fileciteturn1file4L355-L370

而需求要求普通用户不得获得密码、服务端密钥等敏感数据。fileciteturn2file11L994-L999

因此 DTO 必须以最终 API 响应为准。

------

# 分页

所有列表业务要求支持分页。API 输入也明确所有列表型业务必须分页，但默认分页大小尚待确认。fileciteturn2file12L1113-L1119

可以预留概念：

```
PageQuery
PageResult<T>
```

但现在不要自行决定：

```
{
  "page": 1,
  "pageSize": 20,
  "total": 100,
  "items": []
}
```

最终字段可能叫：

```
list
records
items
pagination
meta
totalCount
```

必须等 REST API。

不要创建一个巨大的：

```

```

然后塞几十个可选字段。

# 12. 风险和待确认问题

## P0：当前缺少真正的 REST API 设计文档

这是现在最大的问题。

你上传的是：

> 《API 设计输入文档》

它明确说自己不定义：

```
URL
HTTP Method
HTTP Status
业务错误码
Request JSON
Response JSON
```

fileciteturn0file2L25-L35

所以目前不能正式写：

```
interface CurrentUserResponse
interface EmployeeListResponse
```

也不能正式确定：

```
GET /api/v1/users/me
GET /api/v1/employees
POST /api/v1/leaves
```

这些具体接口。

### 影响

**不影响本次目录架构。**

但会影响下一步真正开发 API 层。

------

## P0：审批工作台的历史访问资格

这是当前前端架构里最值得提前解决的一个点。

业务同时规定：

```
只有负责人获得新增审批能力
```

但：

```
负责人卸任后仍可以查看本人历史审批记录
```

fileciteturn2file13L1188-L1195

因此：

```
isDepartmentManager
```

不能单独决定审批工作台 Route 是否可访问。

最终 CurrentUser API 或相关能力 API 应提供足够信息让前端判断：

```
当前是否有审批入口
```

具体方案由 API 设计决定。

不要前端通过查询所有记录自己猜。

------

## P1：员工页面存在“启用账号”表述不一致

页面需求写了：

```
启用 / 停用
```

fileciteturn2file7L648-L656

但完整项目需求明确描述的是：

```
不删除账号
通过停用处理离职/失效账号
```

没有明确描述“停用后重新启用”的业务流程。fileciteturn2file2L204-L213

而 API 输入当前也主要描述“停用账号”。

所以：

> **停用账号以后能否重新启用：待确认。**

不能因为数据库存在：

```
ENABLED / DISABLED
```

就自动推导“恢复账号”业务。

数据库不能反向增加需求。

------

## P1：管理员是否能使用通讯录

当前仍是明确待确认项。

API 输入写：

```
ADMIN 是否允许通讯录：待产品确认
```

fileciteturn2file4L341-L357

因此 Router 和 Sidebar 初始化前最好确认。

------

## P1：最终 CurrentUser DTO

必须能够支持至少：

```

此外由于“卸任负责人仍能访问历史审批”的规则，很可能还需要某种：

```

或者等价能力。

具体字段不能现在拍脑袋定义。

## P1：认证失效的错误契约

Axios 需要区分：

```

Session 过期
账号停用
密码修改导致 Session 失效

最终 REST API 必须明确：

```

error code

```

否则前端很难可靠做统一认证处理。

## P1：分页统一协议

# 13. 最终架构结论

这个项目不需要 Redux、不需要 React Query、不需要微前端、不需要复杂权限框架。

V1.0 建议稳定保持：

```
React
+
TypeScript
+
Vite
+
Ant Design
+
React Router
+
Zustand
+
Axios
```

总体结构：

```
app
  → 应用骨架

features
  → 业务模块

shared
  → 真正跨业务的公共能力

stores
  → 当前用户认证状态

styles
  → Theme 和全局样式
```

业务模块：

```
auth
profile
dashboard
employees
departments
directory
announcements
leaves
approvals
```

角色模型：

```
ADMIN
EMPLOYEE
```

组织职责：

```
EMPLOYEE
+
当前负责人关系
=
部门负责人能力
```

绝不建立：

```
DEPARTMENT_MANAGER
```

第三种基础角色。

数据库和需求对此已经保持一致。fileciteturn1file9L564-L592

认证模型：

```
HttpOnly Cookie
↓
前端不读取 JWT
↓
应用启动请求 CurrentUser
↓
Zustand 保存 CurrentUser
↓
Router 根据用户状态控制体验
↓
后端继续执行最终权限校验
```

数据管理：

```
CurrentUser
→ Zustand

列表 / 表单 / 筛选 / Loading
→ 页面局部状态

真实业务状态
→ 后端 API 为事实来源
```

因此，这套目录可以作为 **企业 OA V1.0 前端正式架构基线**。

现在真正进入前端编码前，优先级最高的下一项不是继续拆目录，而是把你前面已经做好的 **最终 RESTful API 设计文档** 放进来做一次：

> **“API 契约 ↔ 13 个页面 ↔ 当前前端架构”的最终一致性 Review。**

这一轮通过之后，再初始化 React 项目最稳。
