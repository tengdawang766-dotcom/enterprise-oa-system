# 企业 OA 协同办公系统：六大核心技术复盘与讲解

> 本文基于当前项目的实际实现编写，用于项目复盘、面试准备和后续维护。重点不是背代码，而是理解每项技术解决了什么问题、代码为什么这样组织，以及系统在异常和并发情况下如何保证正确性。

## 0. 阅读方式与系统全景

建议按照下面的顺序学习：

1. 先理解用户如何登录，以及后端如何识别用户。
2. 再理解业务数据如何通过数据库关系组织起来。
3. 用公告模块学习状态流转和幂等。
4. 用请假模块学习状态机、事务和并发。
5. 回到前端，理解页面、状态与接口如何协作。
6. 最后从部署和安全角度把整个系统串起来。

系统请求链路如下：

```text
浏览器
  │
  │  React 页面、Axios 请求、HttpOnly Cookie
  ▼
Nginx（生产环境）
  │
  │  /api 请求反向代理
  ▼
Express
  │
  ├─ 认证中间件：JWT、账号状态、tokenVersion
  ├─ 权限中间件：角色、负责人、数据归属
  ├─ Controller：路由、参数校验、响应
  └─ Service：业务规则、事务、状态流转
  │
  ▼
Prisma ORM
  │
  ▼
MySQL
```

项目采用前后端分离架构：React 负责交互和展示，Express 负责可信的业务判断，Prisma 负责数据库访问，MySQL 保存最终业务事实。

# 1. 登录认证与权限控制

## 1.1 先区分认证与授权

认证回答“你是谁”，授权回答“你能做什么”。

例如：

- 用户使用账号和密码登录，这是认证。
- 只有管理员能创建员工，这是角色授权。
- 只有某条请假申请指定的负责人能审批，这是业务授权。
- 员工只能查看自己的请假记录，这是数据范围授权。

一个完整系统不能只检查是否登录。登录后的用户仍然必须在每个业务入口接受权限判断。

## 1.2 本项目的登录流程

```text
用户提交 username + password
          │
          ▼
Controller 使用 Zod 校验格式
          │
          ▼
AuthService 查询用户
          │
          ├─ 用户不存在 → 401
          ├─ 账号已停用 → 401 ACCOUNT_DISABLED
          └─ bcrypt 校验密码
                    │
                    ├─ 错误 → 401
                    └─ 正确 → 签发 JWT
                                  │
                                  ▼
                         写入 HttpOnly Cookie
```

相关代码：

| 职责 | 文件 |
|---|---|
| 登录、退出、当前用户、修改密码 | `backend/src/modules/auth/` |
| JWT 生成、验证和认证中间件 | `backend/src/common/auth/authentication.ts` |
| 强制改密和角色守卫 | `backend/src/common/auth/` |
| 前端认证状态 | `frontend/src/stores/auth.ts` |
| Axios 与 401 处理 | `frontend/src/lib/axios.ts` |
| 路由守卫 | `frontend/src/components/guards/` |

## 1.3 为什么密码不能明文保存

数据库保存的是 bcrypt 生成的密码哈希 `passwordHash`，不是用户原始密码。

登录时执行的是：

```text
用户输入的密码 + 数据库中的哈希 → bcrypt.compare() → true / false
```

哈希是单向计算。即使数据库泄露，攻击者也不能直接从哈希还原密码。bcrypt 还会加入随机盐，使两个相同密码通常产生不同哈希，降低彩虹表攻击的效果。

## 1.4 JWT 为什么放在 HttpOnly Cookie

JWT 是后端签发的身份凭证，载荷包含：

- `userId`：当前用户 ID；
- `role`：签发时的角色；
- `tokenVersion`：会话版本。

使用 HttpOnly Cookie 的主要价值是：浏览器中的普通 JavaScript 不能读取该 Cookie，可以减少令牌被 XSS 脚本直接窃取的风险。Axios 使用 `withCredentials`，浏览器会在同源或允许携带凭证的请求中自动发送 Cookie。

需要注意：HttpOnly 只限制 JavaScript 读取 Cookie，并不能自动防御所有 XSS 或 CSRF。生产环境还应正确设置：

- `Secure`：只允许 HTTPS 发送；
- `SameSite`：限制跨站携带；
- 合理的 `Domain`、`Path` 和过期时间；
- 跨站部署时配套 CSRF 防护策略。

## 1.5 有 JWT，为什么每次请求还要查数据库

JWT 是自包含的，签发后内容不会自动变化。假设用户登录后发生以下事情：

- 管理员停用了该账号；
- 用户修改了密码；
- 管理员调整了用户角色。

如果后端只验证 JWT 签名，旧令牌在过期前仍可能继续使用。因此本项目的认证中间件在验证签名之后，还会查询用户并检查：

1. 用户仍然存在；
2. 账号状态仍为 `ENABLED`；
3. 数据库中的 `tokenVersion` 与 JWT 一致；
4. 使用数据库中的最新角色和改密状态建立当前用户上下文。

这是一种“JWT 提供身份线索，数据库确认当前有效性”的设计。代价是每次认证请求多一次数据库查询，但换来了账号停用和密码修改的即时生效，适合企业 OA 这类对权限实时性要求较高的系统。

## 1.6 tokenVersion 如何让旧会话失效

假设登录时：

```text
数据库 tokenVersion = 3
JWT tokenVersion = 3
```

修改密码后，数据库在更新密码的同时把 `tokenVersion` 加一：

```text
数据库 tokenVersion = 4
旧 JWT tokenVersion = 3
```

旧 JWT 再次访问时，中间件发现版本不一致，返回 `AUTH_SESSION_EXPIRED`。这样无需维护 JWT 黑名单，也能让该用户之前签发的令牌全部失效。

## 1.7 首次登录强制改密

管理员创建员工时会设置初始密码，并令 `mustChangePassword=true`。登录成功后，用户只能访问白名单接口：

- 查询当前用户；
- 修改密码；
- 退出登录。

访问其他业务接口时，后端返回 `403 PASSWORD_CHANGE_REQUIRED`。修改密码完成后：

1. 保存新密码哈希；
2. 将 `mustChangePassword` 设为 `false`；
3. 增加 `tokenVersion`；
4. 清除当前 Cookie；
5. 用户使用新密码重新登录。

这里必须由后端拦截。仅在前端显示改密页并不安全，因为用户可以跳过页面，直接调用业务 API。

## 1.8 四层权限控制

本项目的权限可以分为四层：

| 层次 | 示例 | 应由谁负责 |
|---|---|---|
| 是否登录 | 未登录不能访问 `/me` | 认证中间件 |
| 是否完成改密 | 首次登录不能使用业务功能 | 强制改密中间件 |
| 基础角色 | 只有 ADMIN 能管理部门和员工 | `requireRole` |
| 业务关系与数据范围 | 只有指定负责人能审批；员工只能看自己的申请 | Service 查询条件与业务判断 |

前端路由守卫和菜单隐藏提供良好的使用体验，但不构成安全边界。真正的权限必须由后端验证，因为 HTTP 请求可以脱离前端页面直接发送。

## 1.9 401、403、404 的区别

- `401 Unauthorized`：没有有效身份，如未登录、令牌过期、账号停用。
- `403 Forbidden`：身份有效，但不允许执行该操作，如普通员工调用管理员接口。
- `404 Not Found`：资源不存在；有时数据归属校验也返回 404，避免向越权用户泄露资源是否存在。

# 2. 数据库关系与 Prisma

## 2.1 数据库设计从业务事实开始

数据库表不是按照页面数量建立的，而是按照需要长期保存的业务事实建立的。本项目的六张核心表是：

```text
users                  用户
  │
  ├── departments      部门与负责人关系
  ├── announcements    公告发布者
  ├── announcement_reads  公告阅读记录
  ├── leave_requests   请假申请与审批人
  └── leave_action_logs 请假操作历史
```

主要关系如下：

```text
departments 1 ────── N users
users       1 ────── 0..1 departments（担任负责人）
users       1 ────── N announcements
users       N ────── N announcements（通过 announcement_reads）
users       1 ────── N leave_requests（申请人）
users       1 ────── N leave_requests（审批人）
leave_requests 1 ─── N leave_action_logs
```

## 2.2 Prisma Schema 的作用

`backend/prisma/schema.prisma` 同时描述：

- 数据表和字段；
- 字段类型和可空性；
- 主键、唯一约束和索引；
- 表之间的关系；
- 枚举状态；
- 数据库字段名映射。

Prisma Client 根据 Schema 生成带类型提示的数据库访问 API。例如关系在 Schema 中定义后，可以在查询时使用 `include` 或 `select` 获取部门、发布者和阅读记录。

## 2.3 User 与 Department 的两种关系

用户与部门之间存在两种不同含义的关系：

1. 员工属于某个部门：`User.departmentId → Department.id`，是多对一。
2. 用户担任某个部门负责人：`Department.managerUserId → User.id`，是一对一或零对一。

`managerUserId` 设置唯一约束意味着同一用户最多负责一个部门。负责人不是单纯的文字字段，而是指向真实用户的外键，因此能够验证：

- 负责人账号必须存在；
- 候选人必须符合部门和账号状态要求；
- 查询员工时可以判断其是否为负责人；
- 请假提交时可以找到实际审批人。

## 2.4 多对多关系为什么需要中间表

一个员工可以阅读多条公告，一条公告也可以被多名员工阅读，这是多对多关系。中间表 `announcement_reads` 不只是连接两边，还保存 `firstReadAt`。

```text
announcement_reads
- id
- announcementId
- userId
- firstReadAt
- unique(announcementId, userId)
```

复合唯一约束表达了一条关键业务规则：同一员工对同一公告最多只有一条阅读记录。相比只在 Service 中先查询再插入，数据库约束在并发请求下也能守住规则。

## 2.5 请假表为什么保存快照字段

`leave_requests` 同时保存申请人、部门和审批人的外键及名称快照，例如：

- `applicantNameSnapshot`；
- `departmentNameSnapshot`；
- `approverNameSnapshot`。

如果只保存外键，员工改名、调部门或负责人更换后，历史请假单显示的信息会跟着变化。审批记录应反映申请发生时的事实，因此使用快照保存历史语义，同时保留外键支持权限判断和关联查询。

这是“当前事实”和“历史事实”的区别：

- `users.name` 是当前姓名；
- `applicantNameSnapshot` 是提交请假时的姓名。

## 2.6 枚举与状态字段

Prisma 枚举让数据库和 TypeScript 对合法值形成明确约束：

- `UserRole`：ADMIN、EMPLOYEE；
- `UserStatus`：ENABLED、DISABLED；
- `AnnouncementStatus`：DRAFT、PUBLISHED、WITHDRAWN；
- `LeaveStatus`：PENDING、APPROVED、REJECTED、CANCELLED；
- `LeaveAction`：SUBMITTED、APPROVED、REJECTED、CANCELLED、EDITED、RESUBMITTED。

枚举能防止拼写错误，但枚举本身不会保证状态流转是否合法。`PUBLISHED` 是否能回到 `DRAFT`、`APPROVED` 是否能撤回，仍需由业务代码控制。

## 2.7 索引如何从查询场景反推

索引应服务真实查询。项目中的常见查询包括：

- 按部门和状态查员工；
- 按公告状态、发布时间分页；
- 按申请人和状态查请假；
- 按审批人和状态查待办；
- 按请假单和时间查操作日志。

因此 Schema 对这些组合建立索引。组合索引的字段顺序应根据查询条件和排序方式设计，不是索引越多越好。索引会增加存储空间，并使新增、修改、删除变慢。

## 2.8 `select` 与 `include`

- `select` 明确只取需要的字段，适合用户、认证等含敏感字段的数据。
- `include` 获取关联对象，适合需要完整关联信息的业务查询。

用户表含 `passwordHash`、`tokenVersion` 等敏感字段。即使 Service 最终没有把它们返回给前端，也建议查询时使用 `select`，减少敏感数据进入内存的范围，并让代码审查者清楚看到接口需要哪些字段。

## 2.9 Migration、Schema 与数据库

三者的职责不同：

- Schema 是当前目标结构；
- Migration 是从旧结构演进到新结构的可执行历史；
- 数据库是实际运行状态。

开发环境修改 Schema 后，应创建并应用 Migration。生产环境使用 `prisma migrate deploy` 执行已经审核和提交的迁移，而不是在生产环境临时生成迁移。

部署前应检查：

1. Migration 文件已提交；
2. 数据库状态与 Migration 一致；
3. 变更是否破坏旧数据；
4. 新增非空字段是否有默认值或迁移策略；
5. 是否准备了备份和回滚方案。

## 2.10 事务与外键删除策略

关系字段还需要明确删除行为：

- 阅读记录和操作日志属于业务记录，删除父记录时如何处理要有明确策略；
- 有员工的部门不应随意删除；
- 担任负责人的用户不能直接停用或调部门，除非先解除关系；
- 已存在业务历史的员工通常应停用，而不是物理删除。

这也是本项目对用户采用状态停用，而没有直接删除员工的重要原因。

# 3. 公告状态流转与阅读幂等

## 3.1 公告状态机

公告有三个状态：

```text
DRAFT（草稿）
  │
  │ 发布
  ▼
PUBLISHED（已发布）
  │
  │ 撤回
  ▼
WITHDRAWN（已撤回）
```

业务规则：

| 当前状态 | 可以编辑 | 可以删除 | 可以发布 | 可以撤回 | 员工可见 |
|---|---:|---:|---:|---:|---:|
| DRAFT | 是 | 是 | 是 | 否 | 否 |
| PUBLISHED | 否 | 否 | 否 | 是 | 是 |
| WITHDRAWN | 否 | 否 | 否 | 否 | 否 |

把状态规则放在后端，可以保证网页、脚本或其他客户端调用同一套规则。

## 3.2 为什么发布不能写成普通 update

如果代码直接执行：

```text
UPDATE announcement SET status = PUBLISHED WHERE id = ?
```

它只检查 ID，没有检查当前状态。两个请求同时发布，或者已撤回公告再次发布，都可能被错误处理。

项目使用带状态条件的原子更新：

```text
UPDATE announcement
SET status = PUBLISHED
WHERE id = ? AND status = DRAFT
```

Prisma 中通过 `updateMany` 把 ID 和预期状态放在同一个 SQL 条件里，再检查受影响行数：

- `count = 1`：状态转换成功；
- `count = 0`：资源不存在，或状态已经变化，需要返回业务冲突。

“先查询状态，再无条件更新”存在检查与更新之间的时间窗口。条件更新把判断交给数据库在一次写操作中完成。

## 3.3 员工只能查询已发布公告

员工端接口无论收到什么参数，都应在数据库查询条件中固定加入：

```text
status = PUBLISHED
```

不能依靠前端过滤草稿和已撤回公告。否则用户可以直接修改请求参数或调用详情接口读取不应公开的内容。

公告详情也要再次验证状态，因为列表不可见不代表详情 URL 不可猜测。

## 3.4 什么是幂等

幂等表示同一个操作执行一次或多次，最终业务结果相同。

员工第一次打开公告：

```text
没有阅读记录 → 新增记录，保存 firstReadAt
```

员工第二次、第三次打开：

```text
已有阅读记录 → 不新增，不修改 firstReadAt
```

最终始终只有一条阅读记录，而且保留首次阅读时间。这就是公告阅读操作的业务幂等。

## 3.5 为什么“先查再插入”不可靠

下面的写法在单请求下看似正确：

```text
1. 查询是否存在阅读记录
2. 不存在则插入
```

两个并发请求可能同时在第 1 步查到“不存在”，然后都执行插入。如果数据库没有唯一约束，就会产生重复记录。

本项目采用两层保证：

1. 数据库复合唯一约束：`unique(announcementId, userId)`；
2. MySQL 原子写入：

```sql
INSERT INTO announcement_reads (...)
VALUES (...)
ON DUPLICATE KEY UPDATE first_read_at = first_read_at;
```

首次请求插入；重复请求触发唯一键冲突后执行一个不改变时间的更新。即使请求并发到达，数据库也只保留一条记录。

## 3.6 为什么不能用普通 upsert 更新当前时间

若冲突时把 `firstReadAt` 更新为当前时间，那么每次打开公告都会覆盖首次阅读时间，字段含义就从“首次阅读时间”变成了“最近阅读时间”。

幂等设计必须先明确业务语义：

- 若要首次阅读时间，冲突时保持原值；
- 若要最近阅读时间，应另设 `lastReadAt`；
- 若要阅读次数，应另设计数或阅读事件表。

不要用一个字段同时承担三个含义。

## 3.7 已读与未读筛选为什么要在数据库完成

错误方式是先分页，再在内存过滤：

```text
数据库取第 1 页 10 条 → 前端或 Service 过滤已读 → 只剩 3 条
```

这会导致：

- 页面数量不足；
- `total` 与实际筛选结果不一致；
- 符合条件的数据可能在后续页，被当前页漏掉。

正确方式是把阅读关系写入 Prisma `where`：

- 已读：当前公告存在该用户的阅读关系 `some`；
- 未读：不存在该用户的阅读关系 `none`。

同一个 `where` 同时用于 `findMany` 和 `count`，分页数据与总数才能一致。

## 3.8 阅读统计的统计口径

统计数字必须使用同一个人群口径。本项目的应读对象是当前启用的普通员工，包括通过部门关系担任负责人的员工，因为负责人基础角色仍是 EMPLOYEE。

```text
应读人数 = ENABLED 且 role=EMPLOYEE 的用户数
已读人数 = 上述人群中存在阅读记录的人数
未读人数 = 应读人数 - 已读人数
阅读率   = 已读人数 / 应读人数
```

如果已读人数统计所有历史用户，而应读人数只统计当前启用用户，就可能出现已读人数大于应读人数。统计接口不仅要会 `count`，还要保证分子与分母属于同一集合。

## 3.9 状态流转与审计的边界

当前 V1 保存公告状态、发布时间、撤回时间和阅读记录，足以完成核心闭环。如果未来需要完整审计，可以增加公告操作日志，记录：

- 谁在什么时间创建；
- 谁修改了哪些字段；
- 谁发布或撤回；
- 发布前后的内容版本。

这属于 V2 的审计增强，不应为了未来可能需求破坏 V1 的交付节奏。

# 4. 请假状态机、事务和并发控制

## 4.1 请假流程为什么比普通 CRUD 复杂

CRUD 只描述增删改查，请假业务还包含：

- 状态只能沿合法方向变化；
- 操作人必须满足业务关系；
- 主记录和操作日志必须同时成功；
- 两个审批请求不能产生两个最终结果；
- 组织结构变化不能改写历史。

因此请假模块的核心不是表单，而是状态机、事务、并发控制和审计。

## 4.2 本项目的请假状态机

```text
创建并提交
    │
    ▼
 PENDING ───────────────► APPROVED
    │                         终态
    ├───────────────────► REJECTED
    │                         终态
    ▼
 CANCELLED
    │
    ├── 编辑 ──► CANCELLED（内容变化，版本递增）
    │
    └── 重新提交 ──► PENDING（重新确定当前审批人）
```

关键规则：

- PENDING 可以撤回、通过或驳回；
- CANCELLED 可以编辑和重新提交；
- APPROVED、REJECTED 是 V1 终态；
- 已处理的申请不能再次审批；
- 驳回必须填写原因；
- 员工只能操作自己的申请；
- 只有申请上记录的审批人才能审批。

## 4.3 请假天数为什么由后端计算

前端提交开始日期和结束日期，后端计算自然日天数：

```text
days = endDate - startDate + 1
```

如果由前端直接提交 `days`，用户可能提交 9 月 1 日至 9 月 3 日，却把天数改成 1。后端根据原始日期计算，才能保证数据一致。

V1 使用自然日。如果业务以后要求工作日、节假日和半天假，需要引入工作日历与更细的时间段模型。

## 4.4 审批人如何确定

提交时根据申请人所属部门查找当前负责人：

1. 员工必须属于一个部门；
2. 部门必须存在负责人；
3. 负责人账号必须可用；
4. 负责人本人不能成为自己的审批人；
5. 把审批人 ID 和名称快照写入请假申请。

重新提交时重新查询当前负责人，这样撤回期间负责人发生变化后，新一轮审批会交给当前负责人。已完成的历史操作仍通过快照保留当时信息。

## 4.5 什么是事务

事务把多条数据库操作视为一个整体，满足“全部成功或全部失败”。

审批通过至少包含两步：

```text
1. leave_requests: PENDING → APPROVED，stateVersion + 1
2. leave_action_logs: 新增 APPROVED 日志
```

如果第 1 步成功、第 2 步失败，而没有事务，申请已显示通过但没有审批日志，业务数据就不完整。

使用 Prisma 事务后：

- 两步都成功，统一提交；
- 任一步失败，全部回滚。

事务解决的是多次写入之间的一致性，但事务本身不自动解决所有并发竞争，还需要条件更新或锁。

## 4.6 乐观并发控制 stateVersion

每条请假申请保存 `stateVersion`。客户端或 Service 在操作时基于读取到的版本执行条件更新：

```text
WHERE id = ?
  AND status = PENDING
  AND stateVersion = 当前版本
```

成功时：

```text
stateVersion = stateVersion + 1
```

假设负责人在两个窗口同时审批同一申请：

```text
窗口 A 读取：PENDING，version=0
窗口 B 读取：PENDING，version=0

A 条件更新成功：APPROVED，version=1
B 再更新时找不到 PENDING 且 version=0 的行，count=0
B 返回状态冲突，不能产生第二个结果
```

这种方式称为乐观锁。它假设冲突不是每次都发生，不长期锁住数据，只在写入时验证版本。

## 4.7 为什么状态和版本要一起判断

只判断版本可以发现数据被修改，但把预期状态也放进条件更清晰：审批操作明确要求当前状态必须是 PENDING。

只判断状态虽然能阻止重复审批，但版本还能识别在相同状态下发生的其他修改。例如撤回申请编辑后仍是 CANCELLED，但内容已经变化、版本已经递增。版本记录了业务对象发生过一次有效变更。

## 4.8 操作日志的版本唯一约束

`leave_action_logs` 对 `(leaveRequestId, stateVersion)` 设置唯一约束，表示同一申请在同一个版本只能有一条对应操作记录。

应用层条件更新负责阻止非法状态转换，数据库唯一约束是最后一道防线。两层共同保证并发情况下不会写出重复的同版本日志。

## 4.9 数据权限要写进查询条件

员工查询自己的请假详情时，应使用：

```text
id = 请求中的申请 ID
AND applicantId = 当前登录用户 ID
```

审批人查询审批详情时，应使用：

```text
id = 请求中的申请 ID
AND approverId = 当前登录用户 ID
```

不要先按 ID 查出记录，再返回前才判断。把归属条件放进查询能够减少敏感数据进入不该进入的代码路径，也能统一返回“不存在或无权查看”。

## 4.10 负责人调整为什么也需要事务

更换或卸任部门负责人时，系统需要检查其是否还有待审批请假。若执行：

```text
1. 查询没有待办
2. 另一个请求创建了待办
3. 卸任负责人
```

就会出现没有审批人的悬空申请。本项目在负责人变更时使用事务和行锁，将“检查待办”与“更新负责人”放在受保护的执行范围内。

这说明并发控制不是请假接口独有的需求。只要“检查条件”和“修改数据”之间不能被其他请求插入，就要考虑条件更新、锁或更高层的业务约束。

## 4.11 错误场景应如何表达

请假接口需要区分：

- 申请不存在；
- 当前用户不是申请人；
- 当前用户不是指定审批人；
- 当前状态不允许操作；
- 版本冲突，申请已被其他请求处理；
- 部门没有负责人；
- 负责人不能自我审批；
- 驳回原因为空。

统一业务错误码能让前端显示准确反馈，也有利于日志检索和自动化测试。

## 4.12 可以继续改进的地方

生产级系统还可补充：

- 明确全系统时区策略，统一日期输入、存储和输出；
- 将请假日期计算扩展到工作日历；
- 在接口层显式传递 `stateVersion`，让用户看到“页面数据已过期”；
- 对审批操作记录操作者 IP、客户端和请求 ID；
- 对关键状态变更发送通知，并使用 Outbox 等方式保证数据库和消息的一致性。

# 5. React 路由、状态管理与接口调用

## 5.1 前端分层

本项目的前端职责大致分为：

```text
pages       页面和业务交互
layouts     管理员/员工整体布局与菜单
components  可复用组件、路由守卫、错误边界
stores      跨页面认证状态
api         后端接口函数
lib         Axios 等基础设施
types       共享 TypeScript 类型
utils       状态标签、密码规则等纯工具
```

分层的目的不是目录好看，而是减少页面对网络、认证和通用规则的重复实现。

## 5.2 React Router 的嵌套路由

路由结构按用户访问范围组织：

```text
/login
/change-password
/app
  ├─ dashboard
  ├─ announcements
  ├─ leave-requests
  ├─ approvals
  ├─ directory
  └─ profile
/app/admin
  ├─ departments
  ├─ employees
  ├─ announcements
  ├─ directory
  └─ profile
```

嵌套路由让同一组页面共享布局：

- 普通员工和负责人使用 `EmployeeLayout`；
- 管理员使用 `AdminLayout`；
- 子页面通过 Outlet 渲染在布局内容区。

## 5.3 路由守卫的执行顺序

典型受保护路由按以下顺序判断：

```text
AuthGuard
   │ 未登录 → /login
   ▼
PasswordChangeGuard
   │ 必须改密 → /change-password
   ▼
RoleGuard（管理端）
   │ 角色不符 → 无权限页
   ▼
业务页面
```

守卫是前端体验控制。后端仍然会再次执行认证、改密和权限验证。

## 5.4 为什么要有认证状态初始化

浏览器刷新后，Zustand 的内存状态会丢失，但 HttpOnly Cookie 仍可能有效。应用启动时调用 `GET /me`：

- 成功：恢复当前用户；
- 401：认为未登录；
- 初始化完成前：显示加载状态，避免页面先跳登录又跳回来。

因此认证状态通常包含：

- `user`：当前用户或 null；
- `initialized`：是否完成会话探测；
- `initAuth()`：恢复会话；
- `login()`、`logout()`、`changePassword()`。

## 5.5 401 为什么通过状态变化触发跳转

Axios 拦截器发现 401 后通知认证 Store 清除用户，`AuthGuard` 观察到 `user=null`，使用 React Router 的 `Navigate` 跳转到登录页。

这个设计保持了单页应用的路由控制。如果在 Axios 中直接执行 `window.location.href='/login'`，会发生整页刷新；初始化期间的 `/me` 401 还可能造成反复刷新和白屏。

网络层负责报告会话失效，路由层负责页面跳转，职责更清晰。

## 5.6 为什么修改密码后不再请求 `/me`

修改密码成功时，后端增加 `tokenVersion` 并清除 Cookie。此时立即调用 `/me` 必然得到 401。正确流程是：

1. 显示修改成功；
2. 清空前端用户状态；
3. 跳转登录页；
4. 使用新密码重新登录。

前端流程必须理解后端的会话语义，否则一个正确的 401 会被误显示为“修改密码失败”。

## 5.7 Axios API 层

Axios 实例统一配置：

- `baseURL=/api/v1`；
- `withCredentials=true`；
- 请求超时；
- 统一 401 处理。

每个业务模块再提供清晰的函数，例如：

```text
announcementApi.getList(params)
leaveApi.cancel(id)
meApi.updateContact(data)
```

页面不需要反复拼接 URL，也不需要知道统一响应的外层结构。类型定义让参数和返回值在开发阶段得到检查。

## 5.8 全局状态与页面状态的边界

并不是所有数据都应该放进 Zustand。

适合全局状态的内容：

- 当前用户；
- 是否完成认证初始化；
- 登录、退出、改密等会话动作。

适合页面内部状态的内容：

- 当前页码；
- 搜索关键字；
- 某个弹窗是否打开；
- 当前表单值；
- 当前页面的列表和加载状态。

如果把所有列表放入全局 Store，会增加失效、同步和清理成本。V1 使用“小而明确的全局认证状态 + 页面局部业务状态”，足以支撑当前规模。

## 5.9 React.lazy 与 Suspense

业务页面使用 `React.lazy` 动态加载。用户访问某个页面时，浏览器才下载对应代码块，降低首次加载体积。

`Suspense` 在代码块加载期间显示加载提示。`ErrorBoundary` 捕获渲染阶段错误，避免整个应用只剩白屏，并给用户重试或返回入口。

动态加载解决的是下载时机，ErrorBoundary 解决的是渲染失败兜底，两者职责不同。

## 5.10 菜单选中状态与稳定引用

Ant Design Menu 的 `selectedKeys` 是数组。如果每次渲染都通过普通函数创建新数组，某些组件内部可能把它视为状态变化，造成额外渲染，严重时形成循环。

项目使用 `useMemo` 根据 `location.pathname` 计算稳定的 `selectedKeys`。这里的经验是：传给复杂组件的对象和数组，如果语义没有变化，应尽量保持引用稳定。

## 5.11 表单与后端校验

前端校验用于及时反馈，后端校验用于保护数据。两边规则应保持一致，例如密码规则和驳回原因：

- 前端立即告诉用户格式错误；
- 后端使用 Zod 再验证一次；
- 数据库约束守住最终边界。

不能因为前端已经校验就省略后端校验。请求可以绕过页面直接发送。

## 5.12 加载、空数据和失败状态

一个完整页面至少要考虑：

- 加载中；
- 加载成功且有数据；
- 加载成功但无数据；
- 请求失败；
- 操作提交中；
- 操作成功；
- 输入错误或业务冲突。

仅用 toast 显示加载失败，用户关闭提示后可能只看到空白。关键页面可以使用 Result 或空状态组件，并提供重试按钮。

# 6. 部署结构与生产安全

## 6.1 生产部署结构

项目准备的容器结构如下：

```text
用户浏览器
    │
    │ HTTPS
    ▼
前端 Nginx 容器
    ├─ 返回 React 静态文件
    ├─ SPA 路由回退到 index.html
    └─ /api 反向代理到 backend
                    │
                    ▼
              Express 容器
                    │
                    ├─ Prisma migrate deploy
                    ├─ Node 进程运行 API
                    └─ 健康检查与优雅退出
                    │
                    ▼
               MySQL 容器
                    │
                    └─ Volume 持久化数据
```

相关文件：

| 文件 | 作用 |
|---|---|
| `docker-compose.yml` | 编排 MySQL、后端、前端及依赖关系 |
| `backend/Dockerfile` | 构建后端生产镜像 |
| `backend/docker-entrypoint.sh` | 启动前执行迁移，再启动服务 |
| `frontend/Dockerfile` | 构建 React，并交给 Nginx 托管 |
| `frontend/nginx.conf` | 静态资源、SPA 回退和 API 代理 |
| `.env.example` | 环境变量示例，不保存真实密码 |

## 6.2 为什么使用多阶段构建

后端和前端 Dockerfile 使用构建阶段与运行阶段分离：

```text
构建阶段：安装开发依赖、编译 TypeScript / 构建 React
运行阶段：只复制运行所需文件和产物
```

好处：

- 运行镜像更小；
- 不携带不必要的编译工具；
- 减少攻击面；
- 构建过程可重复。

## 6.3 Nginx 的两个核心职责

第一，托管前端静态文件。React 构建后是 HTML、CSS 和 JavaScript 文件，不需要 Vite 开发服务器。

第二，反向代理 API。浏览器访问同一个站点下的 `/api`，Nginx 转发到后端容器。这样能简化 Cookie、CORS 和前端环境配置。

SPA 使用前端路由时，直接刷新 `/app/dashboard` 会请求服务器上的该路径。Nginx 必须回退到 `index.html`，再由 React Router 解释路由，否则会返回 404。

## 6.4 容器启动顺序不等于服务可用

`depends_on` 只能表达依赖关系，真正可靠的启动需要健康检查：

1. MySQL 容器启动；
2. 等待数据库能够接受连接；
3. 后端执行 `prisma migrate deploy`；
4. 后端启动并通过健康检查；
5. 前端代理开始对外服务。

进程“已经启动”和服务“已经准备好”不是同一件事。生产系统可以进一步区分：

- liveness：进程是否存活；
- readiness：是否能正常接收请求，包括数据库依赖是否可用。

## 6.5 数据库迁移为什么放在启动流程中

后端代码依赖特定数据库结构。若新代码已经启动而 Migration 未执行，接口可能因字段或表不存在而失败。

使用 `prisma migrate deploy` 可以应用仓库中已有的迁移。生产环境仍应：

- 迁移前备份数据库；
- 评估锁表和执行时间；
- 对破坏性变更采用分阶段发布；
- 保留失败处理与回滚方案。

## 6.6 环境变量与密钥

不应提交到 Git 的内容包括：

- 生产数据库密码；
- JWT Secret；
- 第三方服务密钥；
- 私钥和证书私密部分。

`.env.example` 只列出变量名和安全的示例。真实值应由部署平台、Secret Manager 或受控环境注入。

生产环境中 JWT Secret 缺失时应启动失败，不能回退到公开默认值。密钥还应足够随机，并规划轮换方式。

## 6.7 Cookie、HTTPS 与代理

生产认证 Cookie 应使用 `Secure`，这要求站点通过 HTTPS 访问。如果 TLS 在外层负载均衡或反向代理终止，Express 需要正确理解代理协议，例如合理配置 `trust proxy`，否则可能错误判断连接是否安全。

同域部署最简单：

```text
https://oa.example.com/       前端
https://oa.example.com/api/   后端代理
```

若前后端跨域，则必须同时正确配置 CORS、credentials、Cookie SameSite 和 Secure，配置复杂度更高。

## 6.9 优雅退出

容器停止或发布新版本时，系统会收到终止信号。优雅退出通常执行：

1. 停止接受新请求；
2. 等待正在处理的请求完成；
3. 断开 Prisma 数据库连接；
4. 在超时时间内退出进程。

如果直接强制结束，正在执行的请求可能中断。数据库事务通常会回滚，但用户会收到失败，日志也可能不完整。

## 6.10 日志、监控和可观测性

健康检查只能证明某一时刻接口有响应。生产运行还需要：

- 结构化日志；
- 请求 ID，串联一次请求的所有日志；
- 5xx 错误率和响应时间；
- 登录失败与权限拒绝统计；
- 数据库连接池和慢查询；
- 容器 CPU、内存、磁盘；
- 公告发布、负责人变更、审批等关键审计事件。

日志必须避免输出密码、密码哈希、JWT、Cookie 和完整敏感个人信息。

# 7. 六个主题如何串成一次完整请求

以“负责人审批请假”为例：

```text
1. React 审批页面调用 leave API
2. Axios 自动携带 HttpOnly Cookie
3. Nginx 把 /api 请求转发到 Express
4. 认证中间件验证 JWT，并查询账号状态与 tokenVersion
5. 强制改密中间件检查 mustChangePassword
6. Service 用 approverId 验证当前用户是指定审批人
7. Prisma 开启事务
8. 使用 status + stateVersion 条件更新请假单
9. 写入同版本操作日志
10. MySQL 提交事务
11. 后端返回统一响应
12. React 刷新待办与审批历史
```

这里六个主题同时参与：

- 登录认证决定请求者身份；
- 权限控制决定他是否能审批；
- Prisma 关系找到申请、审批人和日志；
- 状态机决定当前能否通过或驳回；
- 事务与版本控制保证并发正确；
- React、Axios 和路由负责用户交互；
- Nginx、容器和安全配置保证它能在生产结构中运行。

# 11. 从博客迁移到 OA 的设计复盘（已完成）

## 11.1 设计复盘总述

本次迁移不复制框架代码，而是复用业务思想。核心决策：

- **单层讨论**：评论不做嵌套回复，保持扁平结构，降低前端渲染和后端查询复杂度
- **即时反馈**：点赞/收藏使用乐观 UI + 后端幂等，客户端先更新界面再等待服务端确认
- **AI 预览**：AI 仅生成内容预览，不直接写入数据库，用户确认后才保存
- **检索回答**：AI 基于后端真实搜索结果生成回答，不依赖 AI 模型自身知识

## 11.2 点赞设计

前端使用 localStorage 缓存点赞状态（乐观反馈），后端使用 `knowledge_article_likes` 表的 `article_id + user_id` 复合唯一约束保证幂等。点赞操作使用 `INSERT ... ON DUPLICATE KEY UPDATE` 或 Prisma upsert，重复点赞不产生重复记录。取消点赞使用 `DELETE WHERE article_id = ? AND user_id = ?`。

## 11.3 评论设计

评论增加软删除（`deleted_at`）和状态隔离：

- 软删除不物理删除记录，保留 `deleted_by_id`（删除人）、`delete_type`（SELF/ADMIN）、`delete_reason`
- 作者可自行删除自己的评论，管理员可删除任意评论并填写原因
- 查询评论时过滤 `deleted_at IS NOT NULL`，已删除评论对普通用户不可见

## 11.4 审核状态机

新增审核模块，状态机如下：

```text
PUBLISHED（正常发布）
    │
    │ 管理员下架
    ▼
TAKEN_DOWN（已下架）
    │
    │ 作者提交复审
    ▼
PENDING_REVIEW（待审核）
    │
    ├─ 管理员批准 → PUBLISHED
    └─ 管理员驳回 → TAKEN_DOWN
```

每次状态变更记录到 `knowledge_moderation_logs`，包含操作人、原因、变更前后状态。

## 11.5 AI Provider 设计

AI 采用无写权限 Provider 设计：

- `ai-provider.ts` 负责与 AI API 通信，不含任何数据库写操作
- `ai.service.ts` 组合 Provider 调用与业务逻辑
- 服务端根据用户问题先执行真实数据库/搜索查询，将结果作为上下文传给 AI
- AI 返回的内容不直接入库，仅作为预览返回前端
- 内存速率限制：每分钟请求数、并发数、每日配额

## 11.6 未复制的特性

以下博客特性有意不复制到 OA 系统：

- WebSocket 实时推送（OA 场景不需要实时评论通知）
- 长期记忆（AI 不记忆用户历史对话）
- 通用 Agent 框架（仅需问答能力，无需工具调用链）
- MongoDB 存储（继续使用 MySQL + Prisma）

## 11.7 新增一致性问题

迁移引入的新一致性考量：

- **内存速率限制**：重启后重置，多实例不共享，单进程场景下足够
- **Provider 超时处理**：AI 调用设置超时（`AI_TIMEOUT_MS`），超时后返回友好错误，不阻塞用户操作
- **先验证后写入模式**：AI 预览内容经用户确认后才写入数据库，避免 AI 幻觉污染业务数据
