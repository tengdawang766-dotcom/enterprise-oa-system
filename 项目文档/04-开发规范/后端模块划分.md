# 二、Controller 怎么拆

我建议最后控制在 **9 个 Controller 左右**。

| Controller                   | 主要职责                              |
| ---------------------------- | ------------------------------------- |
| `AuthController`             | 登录、退出                            |
| `MeController`               | 当前用户、联系方式、修改密码          |
| `UserController`             | 账号、员工、调部门、重置密码、停用    |
| `DepartmentController`       | 部门 CRUD、负责人候选、任命/更换/卸任 |
| `DirectoryController`        | 企业通讯录                            |
| `AnnouncementController`     | 公告草稿、发布、撤回、公告查询        |
| `AnnouncementReadController` | 打开公告、阅读人员                    |
| `LeaveRequestController`     | 提交、本人的请假、撤销                |
| `ApprovalController`         | 审批候选、待办、历史、通过、驳回      |
| `WorkOverviewController`     | 当前用户工作概览                      |

不要设计一个：

```
OaController
```

然后里面塞四五十个接口。

也不要把负责人单独做成：

```
ManagerController
```

因为负责人本身不是一个独立业务主体。

# 十六、DTO 最重要的设计原则

你后面写代码时要特别注意：

**Request DTO 和 Response DTO 一定分开。**

比如不要搞：

```
UserDTO
```

什么地方都用。

应该：

```
CreateUserRequest
UpdateUserRequest
UserResponse
UserDetailResponse
```

因为这样权限非常清楚。

例如员工修改自己联系方式：

```
UpdateContactRequest
```

只能出现：

```
workEmail
phone
```

那么从 DTO 层面就不可能接收到：

```
role
status
departmentId
```

这叫：

> 尽量让非法状态无法进入业务层。

```
权限专项测试 + 并发专项测试
```

我尤其建议你**不要从请假开始写**。先把用户、部门、负责人关系做稳，再碰请假，否则你后面会不断返回去改前面的组织模型。

# 十八、每一个模块的统一完成标准

以后你每完成一个模块，都按照这 8 项检查：

```
□ Request DTO 完成
□ Response DTO 完成
□ Controller 完成
□ Service 完成
□ Repository 查询完成
□ 权限校验完成
□ 业务错误码完成
□ 正常/异常测试完成
```

涉及状态变化的，再增加：

```
□ 事务检查
□ affected rows 检查
□ 并发测试
□ 历史记录检查
```
