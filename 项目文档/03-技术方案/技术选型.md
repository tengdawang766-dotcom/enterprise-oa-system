# 企业 OA 系统 V1.0 技术选型方案

## 一、核心技术栈

| 层级       | 技术选择                       | 主要用途                                 |
| ---------- | ------------------------------ | ---------------------------------------- |
| 前端框架   | React + TypeScript             | 构建管理后台页面并约束数据类型           |
| 构建工具   | Vite                           | 创建和运行前端项目                       |
| UI组件库   | Ant Design                     | 表格、表单、弹窗、分页、菜单和反馈提示   |
| 前端路由   | React Router                   | 页面跳转、路由守卫和无权限页面处理       |
| 全局状态   | Zustand                        | 管理当前用户、登录状态和必要的全局信息   |
| 接口请求   | Axios                          | 调用后端API、统一处理登录失效和请求错误  |
| 后端       | Node.js + Express + TypeScript | 编写RESTful API和业务逻辑                |
| 数据库     | MySQL                          | 保存人员、部门、公告、阅读记录和请假数据 |
| 数据库访问 | Prisma ORM                     | 定义数据模型、生成迁移、查询MySQL        |
| 登录认证   | JWT                            | 识别当前登录用户                         |
| 密码加密   | bcrypt                         | 对密码进行不可逆哈希                     |
| 参数校验   | Zod                            | 校验请求参数并返回明确错误               |
| 后端日志   | Pino                           | 保存基本运行和错误日志                   |
| 后端测试   | Vitest + Supertest             | 测试接口、权限和请假状态流转             |
| 部署       | Docker Compose + Nginx         | 运行前端、后端和MySQL并提供HTTPS入口     |

## 二、前端方案

### React + TypeScript

React用于将列表、筛选区、表单、状态标签和弹窗拆成可复用组件。TypeScript用于定义用户、部门、公告和请假等数据类型，降低接口字段使用错误。

### Ant Design

本项目包含大量管理后台常见交互：

- 表格与分页。
- 搜索和筛选。
- 新增及编辑表单。
- 审批、撤回等确认弹窗。
- 加载、成功和失败提示。
- 按角色生成的侧边导航。

Ant Design能够减少重复的基础界面工作，把时间集中在权限和业务闭环上。

### React Router

负责页面路由和访问控制：

- 未登录用户访问内部页面时进入登录页。
- 强制修改密码的用户只能访问修改密码和退出功能。
- 登录用户访问无权页面时显示无权限页面。
- 页面权限只改善前端体验，真正的权限仍由后端校验。

### Zustand

只保存确实需要共享的客户端状态：

- 当前登录用户。
- 当前角色和基础权限信息。
- 是否必须修改密码。
- 登录状态初始化结果。

公告、员工和请假列表等服务端数据不长期复制到全局状态中，由各页面通过接口获取并在操作后刷新，减少状态不同步问题。

### Axios

创建统一请求实例，集中处理：

- API基础地址。
- 携带登录凭证。
- 请求超时。
- 统一响应格式。
- 登录失效提示和重新登录。
- 常见错误信息转换。

具体业务错误仍由页面处理，例如日期重叠、没有审批人和申请状态已变化。

## 三、后端方案

### Express + TypeScript

Express负责路由和中间件，TypeScript为请求、响应和业务数据提供类型约束。后端按业务划分为：

- 认证与账号。
- 部门与员工。
- 通讯录。
- 公告。
- 请假审批。
- 工作概览。

建议保持清楚的分层：

```
请求进入
→ 路由匹配
→ 身份认证
→ 权限及参数校验
→ 业务逻辑
→ 数据库访问
→ 统一响应
```

路由层不堆积全部业务逻辑，具体目录结构在系统架构阶段确定。

### Prisma ORM

Prisma用于：

- 定义数据库模型和关系。
- 生成并执行数据库迁移。
- 查询和更新MySQL。
- 提供TypeScript类型。
- 在审批或撤销等操作中使用事务。
- 设置唯一约束及关联关系。

对于两周项目，Prisma可以减少手写重复SQL的工作。涉及并发状态更新时，仍需明确设计条件更新和事务，不能只依赖ORM自动保证。

### Zod

前后端表单校验不能代替后端校验。后端使用Zod校验：

- 必填字段。
- 字符串长度。
- 枚举状态。
- 日期格式。
- 分页和筛选参数。

涉及数据库状态的规则，例如申请日期重叠、审批人资格和当前状态，必须由业务逻辑继续校验。

## 四、登录认证方案

采用JWT认证，登录成功后由后端签发令牌。建议通过由后端设置的 **HttpOnly Cookie** 保存JWT，减少前端脚本直接读取令牌的风险。

JWT至少包含：

- 用户ID。
- 当前角色。
- 令牌版本。
- 签发和过期时间。

后端处理受保护请求时：

1. 读取并验证JWT。
2. 查询当前账号是否仍然启用。
3. 对比账号的令牌版本。
4. 根据当前数据库角色检查接口权限。
5. 业务接口继续检查数据归属。

用户修改或重置密码时，增加账号的令牌版本。旧JWT中的版本与数据库不一致，原有登录状态便会失效。管理员停用账号后，即使旧JWT尚未过期，后端也会因为账号已停用而拒绝请求。

前端隐藏按钮只负责改善体验，不能作为权限保障。

## 五、权限控制方案

本期使用固定RBAC，不制作权限配置中心。

| 角色       | 主要权限                           |
| ---------- | ---------------------------------- |
| 员工       | 公告、通讯录、个人资料和本人请假   |
| 部门负责人 | 员工权限，以及分配给自己的请假审批 |
| 管理员     | 账号、部门、员工和公告管理         |

RBAC只能判断角色是否能够访问一类接口，还需要数据级权限，例如：

- 员工只能查看自己的请假。
- 负责人只能审批指定给自己的申请。
- 管理员不能查看请假详情。
- 原负责人只能查询曾分配给自己的历史记录。
- 用户不能通过修改URL中的编号访问他人数据。

## 六、数据一致性方案

MySQL负责持久化和关系约束，后端负责业务规则。以下操作需要重点保证一致性：

- 同一部门最多存在一名负责人。
- 同一用户对同一公告只有一条阅读记录。
- 审批和撤销同时发生时，只允许一个操作成功。
- 同一申请不能被重复审批。
- 人员存在相关待办时，组织调整必须失败。
- 失败操作不能留下部分更新结果。

审批和撤销不能采用“先查询状态，再无条件更新”的方式。更新时必须同时限定申请仍为待审批状态，并检查实际更新数量；必要时配合数据库事务完成相关记录写入。

## 七、统一响应与异常处理

后端采用统一响应结构，例如：

```
{
  "success": false,
  "code": "LEAVE_STATUS_CHANGED",
  "message": "申请状态已经发生变化，请刷新后查看",
  "data": null
}
```

错误至少区分：

- 参数错误。
- 未登录或登录失效。
- 无权限。
- 数据不存在。
- 业务规则冲突。
- 服务器内部错误。

普通用户只能看到可理解的错误信息，不能看到数据库语句、服务端堆栈或密钥。详细错误写入服务端日志。

## 八、测试与部署方案

### 基本测试

重点编写必要的后端接口测试：

- 登录和停用账号。
- 修改或重置密码后旧登录失效。
- 角色权限与数据归属权限。
- 请假提交规则。
- 通过、驳回、撤销状态流转。
- 重复审批及审批与撤销冲突。
- 公告首次阅读只记录一次。

前端主要进行关键业务流程验证，不追求覆盖所有简单组件。

### 部署

最终使用Docker Compose组织：

- MySQL。
- Express后端。
- React构建产物及Nginx。

Nginx负责：

- 提供前端静态文件。
- 将API请求转发到后端。
- 正式环境配置HTTPS。
- 支持React前端路由刷新。

开发阶段可分别启动前端、后端和MySQL，不必一开始就完成全部部署配置。

## 九、暂不引入的技术

为了控制两周范围，V1.0暂不引入：

- Redux和复杂状态架构。
- Redis。
- 消息队列。
- 微服务。
- WebSocket。
- 通用权限配置引擎。
- 多级审批工作流引擎。
- GraphQL。
- Kubernetes。

只有实际需求证明现有方案无法满足时，才考虑增加新的基础设施。
