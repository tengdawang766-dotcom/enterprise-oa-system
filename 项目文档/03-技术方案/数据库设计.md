# 企业 OA 系统 V1.0 数据库设计

## 一、数据库选择

使用 **MySQL**。

该系统的数据关系明确：

- 用户属于部门。
- 部门关联一名当前负责人，负责人身份仅由部门表维护。
- 公告关联发布人及阅读人员。
- 请假关联申请人、提交时部门和提交时指定的审批人。
- 请假状态只能按照规定流转，并需要处理审批与撤销并发。
- 用户账号不物理删除，历史业务数据需要长期保留。
- 部门如果已经产生人员或历史业务关联，则必须保留；只有完全没有业务关联的空部门允许删除。

关系型数据库适合表达这些关联、唯一约束、外键约束、历史关系和事务要求。

------

# 二、实体与数据表

V1.0 包含以下 6 张核心表：

| 数据表               | 对应实体     | 主要作用                                             |
| -------------------- | ------------ | ---------------------------------------------------- |
| `users`              | 用户         | 保存账号、个人资料、基础角色和账号状态               |
| `departments`        | 部门         | 保存当前部门及当前负责人                             |
| `announcements`      | 公告         | 保存草稿、已发布和已撤回公告                         |
| `announcement_reads` | 公告阅读记录 | 记录每名用户首次阅读公告的时间                       |
| `leave_requests`     | 请假申请     | 保存申请内容、历史快照、审批归属、当前状态及状态版本 |
| `leave_action_logs`  | 请假操作记录 | 保存提交、通过、驳回和撤销的版本化历史动作           |

V1.0 不额外建设：

- 角色权限配置表；
- 多级审批流程表；
- 部门层级表；
- 假期余额表；
- 附件表；
- 消息通知表；
- 通用操作审计平台。

# 三、表关系概览

```
erDiagram
    DEPARTMENTS ||--o{ USERS : "拥有员工"
    USERS o|--o| DEPARTMENTS : "担任当前负责人"

    USERS ||--o{ ANNOUNCEMENTS : "发布"
    USERS ||--o{ ANNOUNCEMENT_READS : "阅读"
    ANNOUNCEMENTS ||--o{ ANNOUNCEMENT_READS : "产生阅读记录"

    USERS ||--o{ LEAVE_REQUESTS : "发起"
    DEPARTMENTS ||--o{ LEAVE_REQUESTS : "提交时所属部门"
    USERS ||--o{ LEAVE_REQUESTS : "提交时被指定为审批人"

    LEAVE_REQUESTS ||--o{ LEAVE_ACTION_LOGS : "产生操作记录"
    USERS ||--o{ LEAVE_ACTION_LOGS : "执行操作"
```

关系说明：

- `users.department_id` 表示用户**当前所属部门**。
- `departments.manager_user_id` 是“谁是当前部门负责人”的**唯一事实来源**。
- `users.role` 只区分系统管理员和企业员工，不保存 `DEPARTMENT_MANAGER`。
- 部门负责人本质上仍然是 `EMPLOYEE`，只是因为其用户编号被某个部门的 `manager_user_id` 引用而获得负责人职责。
- `leave_requests.submitted_department_id` 及其快照字段表达提交请假时的历史事实，不随用户调动、部门改名等变化。
- `leave_requests.approver_id` 表示该申请提交时最终确定的指定审批人。
- 普通员工的审批人由本部门当前负责人确定。
- 当前负责人本人请假时，由其选择另一部门当前符合条件的负责人作为审批人。
- 请假提交后，审批归属固定，不因之后的组织关系变化重新计算。

# 四、`users` 用户表

| 字段                   | 建议类型                   | 约束                 | 说明                         |
| ---------------------- | -------------------------- | -------------------- | ---------------------------- |
| `id`                   | BIGINT                     | 主键，自增           | 用户编号                     |
| `username`             | VARCHAR(50)                | 非空，唯一           | 登录账号，创建后不可修改     |
| `password_hash`        | VARCHAR(255)               | 非空                 | 密码安全哈希值               |
| `name`                 | VARCHAR(50)                | 非空                 | 用户当前姓名                 |
| `role`                 | ENUM('ADMIN','EMPLOYEE')   | 非空                 | 基础角色                     |
| `department_id`        | BIGINT                     | 可空，外键           | 员工当前所属部门；管理员为空 |
| `job_title`            | VARCHAR(100)               | 可空                 | 职务                         |
| `work_email`           | VARCHAR(100)               | 可空                 | 工作邮箱                     |
| `phone`                | VARCHAR(30)                | 可空                 | 联系电话                     |
| `status`               | ENUM('ENABLED','DISABLED') | 非空，默认 `ENABLED` | 账号状态                     |
| `must_change_password` | BOOLEAN                    | 非空，默认 `TRUE`    | 是否必须修改密码             |
| `token_version`        | INT                        | 非空，默认 `0`       | 用于使旧登录凭证失效         |
| `created_at`           | DATETIME                   | 非空                 | 创建时间                     |
| `updated_at`           | DATETIME                   | 非空                 | 更新时间                     |

## 关键约束

- `username` 必须公司内唯一。
- 登录账号创建后不可修改。
- 用户账号不提供物理删除功能。
- 员工离职或失效时，将 `status` 修改为 `DISABLED`。
- `ADMIN.department_id` 必须为空。
- `EMPLOYEE.department_id` 必须有值，并指向当前存在的部门。
- `users.role` 不包含 `DEPARTMENT_MANAGER`。
- 是否是部门负责人不得通过 `users.role` 判断。
- 当前负责人身份必须根据 `departments.manager_user_id` 判断。
- 密码不得保存明文或可逆密文。
- 修改或重置密码时增加 `token_version`，使之前签发的登录凭证失效。
- 停用账号后，不允许该账号重新登录。
- 已经建立的旧登录状态也不能继续访问受保护业务。
- 停用账号不得删除其历史业务关联。

------

## 账号停用前置规则

### 普通员工

如果该员工存在本人：

```
status = PENDING
```

的请假申请：

> 禁止停用账号。

必须先处理完当前待审批业务。

------

### 当前负责人

如果某员工当前还是某部门负责人，则不能直接停用。

必须首先检查：

1. 是否存在本人 `PENDING` 请假；
2. 是否存在 `approver_id = 当前用户` 且 `status = PENDING` 的未处理审批任务。

存在任一情况：

- 禁止更换负责人；
- 禁止卸任负责人；
- 禁止调部门；
- 禁止停用账号。

如果不存在上述待办：

```
更换负责人 / 卸任负责人
↓
解除当前负责人关系
↓
再停用账号
```

### 已确认规则

> 停用账号本身不自动解除 `departments.manager_user_id` 负责人关系。

因此应用层执行停用前必须确认：

```
不存在 departments.manager_user_id = 当前用户.id
```

# 五、`departments` 部门表

| 字段              | 建议类型     | 约束             | 说明                                       |
| ----------------- | ------------ | ---------------- | ------------------------------------------ |
| `id`              | BIGINT       | 主键，自增       | 部门编号                                   |
| `name`            | VARCHAR(100) | 非空，唯一       | 部门当前名称                               |
| `manager_user_id` | BIGINT       | 可空，唯一，外键 | 当前部门负责人，是负责人身份的唯一事实来源 |
| `created_at`      | DATETIME     | 非空             | 创建时间                                   |
| `updated_at`      | DATETIME     | 非空             | 更新时间                                   |

V1.0 **不设置部门状态字段**。

不存在：

```
ENABLED
DISABLED
```

类型的部门生命周期。

------

## 关键约束

- 部门名称公司内唯一。
- `manager_user_id` 可以为空，表示当前部门暂时没有负责人。
- `manager_user_id` 建立唯一约束。
- 一个用户最多担任一个部门的负责人。
- MySQL 唯一索引允许多个 `NULL`，因此多个部门可以同时处于无负责人状态。

被设置为负责人时，用户必须满足：

```
role = EMPLOYEE
status = ENABLED
user.department_id = department.id
```

即：

- 必须是企业员工；
- 账号必须启用；
- 必须属于目标部门。

负责人身份只由：

```
departments.manager_user_id
```

确定。

不再同步维护任何：

```
users.role = DEPARTMENT_MANAGER
```

之类的数据。

------

# 六、部门删除规则

V1.0 支持删除**完全没有业务关联的空部门**。

删除部门前必须检查：

1. 是否存在 `users.department_id = 当前部门`；
2. 是否存在当前负责人；
3. 是否存在 `leave_requests.submitted_department_id = 当前部门`；
4. 是否存在其他必须保留的历史业务关联。

存在任一情况：

> 禁止删除部门。

只有同时满足：

```
无员工
+
无负责人
+
无历史请假
+
无其他历史业务关联
```

时，才能物理删除部门。

## 说明

负责人必须属于该部门，因此正常情况下：

```
存在 manager_user_id
```

意味着同时存在：

```
users.department_id = 当前部门
```

业务层仍应显式检查负责人关系，以避免异常数据或后续扩展造成遗漏。

------

## 为什么不引入部门停用

V1.0 只需要：

- 创建部门；
- 修改部门名称；
- 任命负责人；
- 更换负责人；
- 卸任负责人；
- 删除完全无业务关联的空部门。

不需要：

- 停用部门；
- 恢复部门；
- 向停用部门分配员工；
- 停用部门参与统计等额外生命周期。

这样可以避免为当前约 50 人的单层组织引入不必要的业务复杂度。

# 七、负责人管理规则

## 7.1 任命负责人

管理员选择某部门的员工担任负责人。

必须校验候选用户：

```
role = EMPLOYEE
status = ENABLED
department_id = 目标部门
```

并确认该用户没有负责其他部门。

成功后：

```
departments.manager_user_id = candidate_user_id
```

基础角色仍然：

```
EMPLOYEE
```

------

## 7.2 更换负责人

更换前必须检查旧负责人：

```
本人是否存在 PENDING 请假
```

以及：

```
是否存在 approver_id = old_manager_id
AND status = PENDING
```

存在任一情况：

> 禁止更换。

新负责人必须满足正常负责人候选规则。

更换成功：

```
旧负责人
EMPLOYEE + 负责人职责
↓
EMPLOYEE
```

```
新负责人
EMPLOYEE
↓
EMPLOYEE + 负责人职责
```

两人的 `users.role` 均不发生变化。

------

## 7.3 卸任负责人

由于部门允许没有负责人，因此管理员可以单独卸任负责人。

卸任前必须确认负责人：

- 没有本人待审批申请；
- 没有尚未处理的审批任务。

满足条件后：

```
departments.manager_user_id = NULL
```

原负责人继续作为普通 `EMPLOYEE` 使用系统。

------

## 7.4 负责人调动部门

当前负责人不能直接调离其负责部门。

必须先：

```
检查本人待审批
↓
检查本人审批待办
↓
无待办
↓
更换/卸任负责人
↓
解除负责人关系
↓
再修改 users.department_id
```

历史请假不得随着本次调动改变。

------

## 7.5 无负责人部门

部门允许：

```
manager_user_id = NULL
```

员工仍然可以：

- 登录；
- 查看通讯录；
- 查看公告；
- 查看历史请假；
- 修改允许本人修改的资料。

但普通员工不能提交新的请假，因为没有符合规则的审批人。

系统必须明确说明：

> 当前部门暂无负责人，无法提交请假。

------

# 八、设置、更换和卸任负责人的一致性要求

负责人组织调整涉及跨表查询和业务前置条件，应在同一事务边界内完成关键校验和写入。

更换负责人逻辑示意：

```
START TRANSACTION;

-- 锁定目标部门
SELECT id, manager_user_id
FROM departments
WHERE id = :department_id
FOR UPDATE;

-- 检查旧负责人是否存在本人待审批请假
SELECT id
FROM leave_requests
WHERE applicant_id = :old_manager_id
  AND status = 'PENDING'
LIMIT 1
FOR UPDATE;

-- 检查旧负责人是否存在未处理审批任务
SELECT id
FROM leave_requests
WHERE approver_id = :old_manager_id
  AND status = 'PENDING'
LIMIT 1
FOR UPDATE;

-- 锁定并校验新负责人候选人
SELECT id, role, department_id, status
FROM users
WHERE id = :new_manager_user_id
FOR UPDATE;

-- 应用层校验：
-- role = 'EMPLOYEE'
-- status = 'ENABLED'
-- department_id = :department_id
-- 不负责其他部门

UPDATE departments
SET manager_user_id = :new_manager_user_id,
    updated_at = NOW()
WHERE id = :department_id;

COMMIT;
```

存在任何不符合条件情况时必须回滚。

# 九、`announcements` 公告表

| 字段           | 建议类型                              | 约束               | 说明                   |
| -------------- | ------------------------------------- | ------------------ | ---------------------- |
| `id`           | BIGINT                                | 主键，自增         | 公告编号               |
| `title`        | VARCHAR(200)                          | 非空               | 公告标题               |
| `content`      | TEXT                                  | 非空               | 公告正文               |
| `status`       | ENUM('DRAFT','PUBLISHED','WITHDRAWN') | 非空，默认 `DRAFT` | 公告状态               |
| `publisher_id` | BIGINT                                | 非空，外键         | 创建并发布公告的管理员 |
| `published_at` | DATETIME                              | 可空               | 首次发布时间           |
| `withdrawn_at` | DATETIME                              | 可空               | 撤回时间               |
| `created_at`   | DATETIME                              | 非空               | 创建时间               |
| `updated_at`   | DATETIME                              | 非空               | 更新时间               |

## 关键约束

- 新建公告默认 `DRAFT`。
- 草稿可以编辑。
- 草稿可以删除。
- 发布时：

```
DRAFT → PUBLISHED
```

并记录 `published_at`。

- 撤回时：

```
PUBLISHED → WITHDRAWN
```

并记录 `withdrawn_at`。

- 已发布公告禁止编辑。
- 已发布公告禁止删除。
- 已撤回公告禁止编辑。
- 已撤回公告禁止删除。
- 已撤回公告禁止重新发布。
- 公告发布人必须为当前启用的 `ADMIN`。
- 公告状态变化必须由后端检查当前状态。
- 重要状态更新应使用带状态条件的更新，防止重复发布和重复撤回。

# 十、`announcement_reads` 公告阅读记录表

| 字段              | 建议类型 | 约束       | 说明                 |
| ----------------- | -------- | ---------- | -------------------- |
| `id`              | BIGINT   | 主键，自增 | 阅读记录编号         |
| `announcement_id` | BIGINT   | 非空，外键 | 被阅读公告           |
| `user_id`         | BIGINT   | 非空，外键 | 阅读公告的员工       |
| `first_read_at`   | DATETIME | 非空       | 首次成功打开详情时间 |

建立联合唯一约束：

```
UNIQUE (announcement_id, user_id)
```

## 业务规则

同一员工对同一公告最多一条有效阅读记录。

首次打开：

```
不存在记录
↓
创建记录
↓
保存 first_read_at
```

重复打开：

```
已有记录
↓
保持 first_read_at 不变
```

不得覆盖为最近阅读时间。

其他规则：

- 只有启用 `EMPLOYEE` 阅读员工公告时产生记录。
- 管理员查看公告不产生员工阅读记录。
- 只有成功打开当前仍为 `PUBLISHED` 的公告详情才记为已读。
- 已撤回公告保留历史阅读记录。

------

## 并发重复阅读

可使用数据库唯一约束完成幂等写入：

```
INSERT INTO announcement_reads (
    announcement_id,
    user_id,
    first_read_at
)
VALUES (
    :announcement_id,
    :user_id,
    NOW()
)
ON DUPLICATE KEY UPDATE
    first_read_at = first_read_at;
```

即使同一用户同时多次打开公告：

> 仍只保留第一次成功写入的阅读时间。

# 十二、请假历史快照

如果未来：

- 员工改名；
- 员工调部门；
- 部门改名；
- 负责人更换；
- 负责人卸任；
- 用户停用；

仅依赖当前关联表无法准确表达请假提交时的历史事实。

因此请假表必须保留：

```
applicant_name_snapshot
submitted_department_id
department_name_snapshot
approver_id
approver_name_snapshot
```

历史详情展示时应优先使用快照字段描述提交时业务事实。

例如：

```
2026-09-01
张三属于技术部并提交请假

2026-10-01
张三调到产品部
```

历史申请仍然展示：

```
提交部门：技术部
```

而不是产品部。

外键负责保持实体关联。

快照负责保持历史事实。

两者表达不同含义，不属于双数据源风险。

------

# 十三、请假审批人确定规则

这是请假提交时最重要的业务规则之一。

审批人根据申请人是否当前承担负责人职责分为两类。

------

## 13.1 普通员工提交请假

如果申请人不是其所在部门的当前负责人：

审批人自动确定为：

```
申请人当前所属部门
↓
departments.manager_user_id
↓
approver_id
```

提交前必须确认：

- 申请人是启用 `EMPLOYEE`；
- 申请人有当前所属部门；
- 当前部门存在负责人；
- 当前负责人账号启用；
- 当前负责人确实属于该部门。

如果当前部门：

```
manager_user_id = NULL
```

则禁止提交。

------

## 13.2 当前负责人本人提交请假

如果：

```
申请人.id
=
申请人所属部门.manager_user_id
```

说明申请人当前承担部门负责人职责。

此时不能继续使用本部门负责人作为审批人，否则会出现自己审批自己。

负责人本人提交时：

> 必须主动选择另一部门当前符合条件的负责人作为审批人。

合法候选人必须满足：

```
role = EMPLOYEE
status = ENABLED
```

并且：

```
存在 departments.manager_user_id = candidate_user_id
```

同时：

```
candidate_department_id != applicant_department_id
```

并且：

```
candidate_user_id != applicant_id
```

即：

- 必须是启用员工；
- 必须当前真实承担另一个部门负责人职责；
- 必须是另一部门负责人；
- 不能选择本人。

没有符合条件的候选人：

> 禁止提交请假，并明确说明当前没有可用审批人。

------

## 13.3 审批人提交后固定

无论普通员工还是当前负责人：

一旦提交成功：

```
leave_requests.approver_id
```

即成为该申请固定审批归属。

后续不能根据组织关系重新动态计算。

因此：

- 部门负责人变化不修改历史申请；
- 申请人调部门不修改历史申请；
- 部门改名不修改历史申请。

------

# 十四、请假申请业务规则

后端提交申请时必须检查：

- 申请人是 `ENABLED` 的 `EMPLOYEE`。
- 申请人存在当前所属部门。
- 根据申请人是否为当前负责人执行对应审批人确定规则。
- 日期格式正确。
- 开始日期不得早于北京时间提交当天。
- 结束日期不得早于开始日期。
- 请假天数由后端计算。
- 不信任客户端自行传入的天数。
- 天数按开始、结束首尾都包含的自然日计算。
- 周末和节假日照常计入。
- 单次最多 30 天。
- 请假类型只能为：
  - `PERSONAL`
  - `SICK`
  - `ANNUAL`
- 请假原因必填。
- 原因最多 500 字。
- 申请人和审批人不得相同。
- 与本人现有 `PENDING` 或 `APPROVED` 申请不得发生日期重叠。

------

## 日期区间重叠判断

两个闭区间发生重叠的条件：

```
已有申请.start_date <= 新申请.end_date
并且
已有申请.end_date >= 新申请.start_date
```

满足两个条件：

> 日期发生重叠。

只需要检查已有：

```
PENDING
APPROVED
```

申请。

以下状态不占用日期：

```
REJECTED
CANCELLED
```

------

# 十五、请假状态与版本规则

创建申请时：

```
status = PENDING
state_version = 0
```

合法状态流转只有：

```
PENDING → APPROVED
PENDING → REJECTED
PENDING → CANCELLED
```

其中：

- `APPROVED`
- `REJECTED`
- `CANCELLED`

均为最终状态。

进入最终状态后：

- 不能编辑；
- 不能删除；
- 不能再次审批；
- 不能再次撤销；
- 不允许再次发生状态流转。

每次成功状态变化：

```
state_version = state_version + 1
```

状态更新必须同时匹配：

- 当前状态；
- 预期版本号。

不得：

```
先 SELECT 状态
↓
再无条件 UPDATE
```

------

# 十六、`leave_action_logs` 请假操作记录表

| 字段                     | 建议类型                                            | 约束       | 说明               |
| ------------------------ | --------------------------------------------------- | ---------- | ------------------ |
| `id`                     | BIGINT                                              | 主键，自增 | 操作记录编号       |
| `leave_request_id`       | BIGINT                                              | 非空，外键 | 对应请假申请       |
| `action`                 | ENUM('SUBMITTED','APPROVED','REJECTED','CANCELLED') | 非空       | 操作类型           |
| `operator_id`            | BIGINT                                              | 非空，外键 | 实际操作人         |
| `operator_name_snapshot` | VARCHAR(50)                                         | 非空       | 操作时人员姓名     |
| `comment`                | VARCHAR(500)                                        | 可空       | 审批意见或驳回原因 |
| `state_version`          | INT                                                 | 非空       | 本动作对应申请版本 |
| `created_at`             | DATETIME                                            | 非空       | 操作发生时间       |

建立联合唯一约束：

```
UNIQUE (leave_request_id, state_version)
```

------

## 版本与日志关系

申请提交：

```
SUBMITTED
state_version = 0
```

第一次最终状态变化：

```
APPROVED / REJECTED / CANCELLED
state_version = 1
```

V1.0 只有：

```
PENDING → 最终状态
```

一次状态变化。

因此正常情况下每个申请包含：

```
version 0：SUBMITTED
version 1：最终操作
```

两条操作记录。

联合唯一约束：

```
UNIQUE(leave_request_id, state_version)
```

保证：

> 同一个申请的同一个状态版本不能产生两个操作日志。

------

## 其他日志规则

- 提交申请必须写入 `SUBMITTED`。
- 通过必须写入 `APPROVED`。
- 驳回必须写入 `REJECTED`。
- 撤销必须写入 `CANCELLED`。
- 驳回时 `comment` 必填。
- 通过时 `comment` 可空。
- 审批意见或驳回原因最多 500 字。
- 日志不允许修改。
- 日志不允许删除。
- 当前状态以 `leave_requests.status` 为准。
- 历史处理过程以 `leave_action_logs` 为准。
- 状态更新和日志写入必须处于同一事务。

------

# 十七、请假提交事务

创建申请和写入提交日志必须在同一个事务内完成。

示意：

```
START TRANSACTION;

INSERT INTO leave_requests (
    applicant_id,
    applicant_name_snapshot,
    submitted_department_id,
    department_name_snapshot,
    approver_id,
    approver_name_snapshot,
    leave_type,
    start_date,
    end_date,
    days,
    reason,
    status,
    state_version,
    created_at,
    updated_at
)
VALUES (
    :applicant_id,
    :applicant_name,
    :department_id,
    :department_name,
    :approver_id,
    :approver_name,
    :leave_type,
    :start_date,
    :end_date,
    :days,
    :reason,
    'PENDING',
    0,
    NOW(),
    NOW()
);

SET @leave_request_id = LAST_INSERT_ID();

INSERT INTO leave_action_logs (
    leave_request_id,
    action,
    operator_id,
    operator_name_snapshot,
    comment,
    state_version,
    created_at
)
VALUES (
    @leave_request_id,
    'SUBMITTED',
    :applicant_id,
    :applicant_name,
    NULL,
    0,
    NOW()
);

COMMIT;
```

任一步失败：

> 整体回滚。

不能产生：

```
有申请但没有提交日志
```

或者：

```
有提交日志但没有申请
```

的半完成数据。

------

# 十八、审批与撤销并发控制

审批、驳回、撤销必须使用：

```
条件更新
+
state_version
+
事务
+
affected_rows 检查
```

共同保证。

------

## 18.1 审批通过

```
START TRANSACTION;

UPDATE leave_requests
SET status = 'APPROVED',
    state_version = state_version + 1,
    updated_at = NOW()
WHERE id = :leave_request_id
  AND approver_id = :operator_id
  AND status = 'PENDING'
  AND state_version = :expected_version;
```

应用层必须立即判断：

```
affected_rows = 1
```

只有成功更新 1 行，才能继续写日志。

否则：

```
ROLLBACK
```

并重新判断实际原因，例如：

- 当前用户不是指定审批人；
- 申请已经通过；
- 已经驳回；
- 已经撤销；
- 版本已经发生变化。

成功后：

```
INSERT INTO leave_action_logs (
    leave_request_id,
    action,
    operator_id,
    operator_name_snapshot,
    comment,
    state_version,
    created_at
)
VALUES (
    :leave_request_id,
    'APPROVED',
    :operator_id,
    :operator_name,
    :comment,
    :expected_version + 1,
    NOW()
);

COMMIT;
```

------

## 18.2 驳回

采用相同并发结构：

```
PENDING → REJECTED
```

但必须保证：

```
comment 非空
长度 <= 500
```

------

## 18.3 员工撤销

```
START TRANSACTION;

UPDATE leave_requests
SET status = 'CANCELLED',
    state_version = state_version + 1,
    updated_at = NOW()
WHERE id = :leave_request_id
  AND applicant_id = :operator_id
  AND status = 'PENDING'
  AND state_version = :expected_version;
```

只有：

```
affected_rows = 1
```

才可以继续：

```
INSERT INTO leave_action_logs (
    leave_request_id,
    action,
    operator_id,
    operator_name_snapshot,
    comment,
    state_version,
    created_at
)
VALUES (
    :leave_request_id,
    'CANCELLED',
    :operator_id,
    :operator_name,
    NULL,
    :expected_version + 1,
    NOW()
);

COMMIT;
```

更新失败：

> 不得写撤销日志。

------

# 十九、审批与撤销同时发生

例如申请当前：

```
status = PENDING
state_version = 0
```

员工同时点击撤销，审批人同时点击通过。

两个操作分别尝试：

```
PENDING / version 0
→ APPROVED / version 1
```

和：

```
PENDING / version 0
→ CANCELLED / version 1
```

数据库只允许其中一个条件更新成功。

成功方：

```
affected_rows = 1
```

并写入 version 1 日志。

失败方：

```
affected_rows = 0
```

必须回滚。

再加上：

```
UNIQUE (leave_request_id, state_version)
```

因此 version 1 不可能同时出现：

```
APPROVED
CANCELLED
```

两个动作。

最终能够保证：

> 一张请假申请只能产生一个最终状态。

------

# 二十、负责人调整与待审批任务

V1.0 已明确：

如果当前负责人存在：

```
approver_id = 当前负责人
AND
status = PENDING
```

则禁止：

- 更换负责人；
- 卸任负责人；
- 调离部门；
- 停用账号。

因此正常业务流程中不会出现：

```
负责人已经卸任或停用
但仍遗留未处理审批任务
```

的情况。

同样，如果负责人存在本人：

```
applicant_id = 当前负责人
AND
status = PENDING
```

也禁止上述组织调整。

------

## 历史已完成申请

负责人完成历史审批以后：

即使后来：

- 被更换；
- 被卸任；
- 调部门；
- 停用；

历史：

```
approver_id
approver_name_snapshot
leave_action_logs
```

仍然保留。

其历史处理记录可以继续查询。

# 二十二、外键与删除策略

本项目重视历史数据。

默认原则：

> 不使用级联删除清除用户、请假和审批历史。

建议重要历史关联采用：

```
ON DELETE RESTRICT
```

------

## 删除策略

| 数据对象           | 删除策略                   |
| ------------------ | -------------------------- |
| 用户               | 不允许物理删除，只允许停用 |
| 部门               | 完全无业务关联时允许删除   |
| 有员工的部门       | 禁止删除                   |
| 有当前负责人的部门 | 禁止删除                   |
| 有历史请假的部门   | 禁止删除                   |
| 公告草稿           | 允许按业务规则删除         |
| 已发布公告         | 禁止删除                   |
| 已撤回公告         | 禁止删除                   |
| 公告阅读记录       | 不单独删除                 |
| 请假申请           | 不允许删除                 |
| 请假操作记录       | 不允许删除                 |

------

## 建议外键动作

```
users.department_id
→ departments.id
ON DELETE RESTRICT
```

这样有当前员工的部门无法删除。

```
departments.manager_user_id
→ users.id
ON DELETE RESTRICT
```

用户本身不物理删除，同时避免异常删除破坏负责人关系。

```
announcements.publisher_id
→ users.id
ON DELETE RESTRICT
```

```
announcement_reads.announcement_id
→ announcements.id
ON DELETE RESTRICT
```

```
announcement_reads.user_id
→ users.id
ON DELETE RESTRICT
```

```
leave_requests.applicant_id
→ users.id
ON DELETE RESTRICT
```

```
leave_requests.submitted_department_id
→ departments.id
ON DELETE RESTRICT
```

因此一旦部门被历史请假引用：

> 数据库直接阻止删除。

```
leave_requests.approver_id
→ users.id
ON DELETE RESTRICT
```

```
leave_action_logs.leave_request_id
→ leave_requests.id
ON DELETE RESTRICT
```

```
leave_action_logs.operator_id
→ users.id
ON DELETE RESTRICT
```

# 二十三、需要事务或原子控制的业务

以下操作需要事务、条件更新或等价的一致性机制：

1. 任命部门负责人。
2. 更换部门负责人。
3. 卸任部门负责人。
4. 调整员工所属部门。
5. 负责人解除职责后停用账号。
6. 提交请假并写入 `SUBMITTED` 日志。
7. 通过请假并写入 `APPROVED` 日志。
8. 驳回请假并写入 `REJECTED` 日志。
9. 撤销请假并写入 `CANCELLED` 日志。
10. 修改密码并使旧登录状态失效。
11. 管理员重置密码并使旧登录状态失效。
12. 公告首次阅读并发幂等写入。
13. 公告发布和撤回的状态条件更新。

# 二十四、组织调整并发要求

负责人更换、卸任、调动、停用时，都需要防止以下竞态：

```
管理员检查：
负责人目前没有待审批任务
↓
检查刚结束
↓
另一名员工恰好提交请假给该负责人
↓
管理员继续卸任负责人
```

最终就可能造成：

```
负责人已卸任
+
新产生 PENDING 审批任务
```

因此负责人组织调整与审批归属检查必须设计成一致的业务操作。

具体采用：

- 行锁；
- 事务隔离；
- 条件更新；
- 其他并发控制；

由实现阶段决定。

数据库设计阶段只明确最终要求：

> 负责人组织关系变化不能与新审批任务产生互相矛盾的数据。

# 二十六、真实业务场景检查

| 业务场景                           | 设计结论 | 保证机制                                             |
| ---------------------------------- | -------- | ---------------------------------------------------- |
| 公告重复打开只保留首次阅读时间     | 支持     | 阅读联合唯一约束 + 幂等写入                          |
| 员工调部门后历史请假显示提交时部门 | 支持     | 部门外键 + 部门名称快照                              |
| 部门改名后历史请假仍显示原名称     | 支持     | `department_name_snapshot`                           |
| 审批和撤销同时发生只能产生一个结果 | 支持     | 状态条件 + `state_version` + 事务 + 日志版本唯一约束 |
| 账号停用后历史数据完整             | 支持     | 用户不物理删除 + 外键限制 + 快照                     |
| 更换负责人不会产生双数据源         | 支持     | `manager_user_id` 唯一负责人事实来源                 |
| 负责人卸任后仍为普通员工           | 支持     | 基础角色始终为 `EMPLOYEE`                            |
| 负责人有审批待办时禁止卸任         | 支持     | `approver_id + status` 检查                          |
| 负责人有本人待审批时禁止卸任       | 支持     | `applicant_id + status` 检查                         |
| 当前负责人不能直接停用             | 支持     | 先解除负责人关系，再停用                             |
| 普通员工提交请假由本部门负责人审批 | 支持     | 提交时读取本部门 `manager_user_id`                   |
| 当前负责人本人能够提交请假         | 支持     | 选择另一部门当前负责人                               |
| 负责人不能自己审批自己             | 支持     | 申请人与审批人校验                                   |
| 更换负责人后历史审批归属保持不变   | 支持     | `approver_id` 和审批人快照固定                       |
| 无负责人部门员工不能提交请假       | 支持     | 提交前检查 `manager_user_id`                         |
| 空部门误建后可以删除               | 支持     | 无员工、负责人、历史业务时允许删除                   |
| 有员工部门不能删除                 | 支持     | 业务检查 + FK RESTRICT                               |
| 有历史请假部门不能删除             | 支持     | `submitted_department_id` FK RESTRICT                |
| 工作概览与实际业务一致             | 支持     | 直接查询当前业务表，不维护冗余统计数据               |

# 二十九、核心设计原则

本版最终遵循以下原则：

## 1. 当前事实只保留一个权威来源

部门负责人只由：

```
departments.manager_user_id
```

决定。

不再同时使用用户角色保存负责人身份。

------

## 2. 当前事实与历史事实分开

例如：

```
users.department_id
```

表达：

> 员工现在属于哪个部门。

而：

```
leave_requests.submitted_department_id
department_name_snapshot
```

表达：

> 员工提交这张请假时属于哪个部门。

两个字段含义不同。

------

## 3. 历史业务不能随组织调整重写

人员：

- 改名；
- 调部门；
- 停用；

部门：

- 改名；

负责人：

- 更换；
- 卸任；

均不能改变已经发生的请假历史。

------

## 4. 用户停用而不是删除

历史业务通过用户外键继续保留。

------

## 5. 部门只在完全无业务关联时删除

没有历史价值的空部门允许删除。

一旦产生：

- 员工；
- 负责人；
- 历史请假；

等业务关联，即禁止删除。

V1.0 不引入部门状态。

------

## 6. 状态变化必须防止并发冲突

请假通过、驳回、撤销采用：

```
条件更新
+
state_version
+
事务
+
affected_rows
+
日志版本唯一约束
```

共同控制。

------

## 7. 权限不能仅依赖数据库字段表面值

例如审批某张请假，不能只判断：

```
当前用户是不是负责人
```

还必须判断：

```
leave_requests.approver_id
=
当前用户.id
```

负责人只能处理明确分配给自己的申请。

------

# 三十、最终结论

本版数据库设计已经与《企业 OA 协同办公系统 V1.0 API 设计输入文档》的核心业务规则完成统一。

已经解决此前存在的主要冲突：

1. 部门负责人不再作为独立基础角色。
2. 删除部门启用/停用生命周期。
3. 空部门允许删除。
4. 有历史关联部门禁止删除。
5. 当前负责人必须先更换或卸任后才能停用账号。
6. 有本人待审批或审批待办的负责人禁止组织调整。
7. 当前负责人本人请假时支持选择另一部门当前负责人审批。
8. 普通员工和负责人使用不同的审批人确定规则。
9. 已提交请假的历史审批归属固定。
10. 请假审批和撤销并发只能产生一个最终结果。

因此本版已经可以作为：

> **后续 RESTful API 设计、Prisma Schema 设计以及最终 MySQL 建表 SQL 的数据库设计依据。**

后续如果 API 设计与本数据库设计发生冲突：

> 首先检查是否属于产品业务规则变化。

数据库设计不得自行覆盖已经确认的产品业务规则。
