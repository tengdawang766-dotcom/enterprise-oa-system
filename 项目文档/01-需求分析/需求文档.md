# 企业 OA 协同办公系统 V1.0 项目需求

## 一、项目背景

一家约 50 人的小型企业，目前主要通过聊天群、私聊和电子表格处理日常办公事务：

- 员工不知道去哪里查找同事及部门信息。
- 公司公告混在聊天记录中，难以确认谁已阅读。
- 请假通过私聊审批，申请进度不透明，历史记录不完整。
- 行政人员重复维护员工信息，部门负责人难以集中处理待办。

企业希望建设一套内部 OA 系统，将人员信息、公告和请假审批集中管理。

本期面向单一企业，以完成日常办公业务闭环为目标，不建设大型通用 OA 平台。

## 二、项目目标与使用场景

V1.0 应支持以下实际场景：

1. 新员工入职后，管理员建立账号并分配部门，员工能够登录使用。
2. 员工查找同事的部门、职务和工作联系方式。
3. 管理员发布公司公告，员工阅读，管理员查看阅读情况。
4. 员工提交请假申请，部门负责人审批，员工查看结果及处理记录。
5. 员工离职后，管理员停用账号，历史业务记录仍可追溯。

系统需要提供完整的前端、后端和持久化数据存储，最终能够部署并通过浏览器实际使用。

## 三、用户角色

| 角色       | 主要工作                                           | 权限范围                   |
| ---------- | -------------------------------------------------- | -------------------------- |
| 普通员工   | 查阅公告与通讯录、维护个人联系方式、提交和查询请假 | 公共信息及本人业务         |
| 部门负责人 | 完成员工日常操作，处理本部门员工的请假申请         | 本人业务及分配给自己的审批 |
| 系统管理员 | 管理账号、部门、负责人和公告                       | 全公司基础管理及公告管理   |

补充约定：

- 每个账号只有一种基础账号身份：系统管理员或企业员工。部门负责人属于员工承担的组织职责，不作为独立基础角色。员工被任命为部门负责人后获得对应审批能力；负责人被更换或卸任后自动失去负责人权限，继续作为普通员工使用系统。 
- 部门负责人同时拥有普通员工的日常使用能力。
- 系统管理员使用独立管理账号，不参与请假，也不拥有请假审批权。
- 员工和部门负责人必须归属一个部门；系统管理员不归属部门。
- 每个部门最多有一名负责人，一个负责人只能负责自己所属的部门。
- 本期不提供自定义角色或自定义权限配置。

## 四、核心业务需求与规则

### 4.1 账号与个人信息

**账号管理**

- 账号由系统管理员创建，不开放自行注册。
- 登录账号在公司内唯一，创建后不可修改。
- 账号信息包括姓名、角色、所属部门、职务、工作邮箱、联系电话和启用状态。
- 姓名、角色必填；员工及负责人还必须指定部门；其他资料允许暂缺。
- 管理员设置初始密码；首次登录必须修改密码后才能使用其他业务。
- 忘记密码时，由管理员重置密码，重置后须重新登录并修改密码。
- 不支持删除账号，通过停用处理离职或失效账号。
- 管理员不能停用自己的账号。

**个人使用**

- 用户能够登录、退出和修改本人密码。
- 用户能够查看个人资料，修改本人工作邮箱和联系电话。
- 姓名、部门、角色、职务由管理员维护。
- 密码至少 8 位，包含字母和数字。
- 密查询界面显示，已登录的码不得以明文保存。
- 账号停用后不能登录；也不得在账号也不能继续访问受保护业务。
- 密码修改或重置后，原有登录状态失效。

### 4.2 部门与员工管理

- 企业采用单层部门结构，不设子部门。
- 部门名称必填且在公司内唯一。
- 管理员可以新增部门、修改部门名称、分配或更换负责人。
- 部门负责人必须是该部门内的启用账号。
- 部门允许暂时没有负责人，但该部门员工在此期间不能提交请假，系统应明确说明原因。
- 部门中存在任何关联账号或历史申请时，不允许删除。
- 更换负责人后，原负责人恢复为普通员工。

为避免审批归属不明确，本期采用以下限制：

- 员工存在待审批申请时，不允许调动部门、变更角色或停用账号。
- 负责人存在本人待审批申请，或有尚未处理的审批任务时，不允许更换、调动、变更角色或停用。
- 上述限制应明确提示具体原因，不能只显示“操作失败”。

### 4.3 企业通讯录

- 启用状态的员工和部门负责人出现在通讯录中。
- 支持按姓名搜索、按部门筛选，并查看姓名、部门、职务、工作邮箱和联系电话。
- 停用账号和独立管理账号不出现在通讯录中。
- 通讯录不公开请假记录、密码或其他非公开信息。
- 普通员工和负责人都不能修改他人的通讯录资料。

### 4.4 公司公告

**公告维护**

- 系统管理员可以创建、编辑和删除公告草稿。
- 公告包含标题、正文、发布人和发布时间。
- 标题、正文必填；正文使用纯文本即可。
- 公告状态包括草稿、已发布、已撤回。
- 草稿仅管理员可见。
- 发布后，全体启用员工及负责人可见。
- 已发布公告不可直接修改，内容有误时应撤回，再新建公告发布。
- 已撤回公告不再向员工展示，管理员仍能查阅内容和阅读记录。
- 已发布和已撤回公告均不允许删除。

**公告阅读**

- 员工和负责人可以查看公告列表及详情，按标题搜索，并区分已读、未读。
- 用户首次打开公告详情时记为已读，记录首次阅读时间。
- 重复打开不重复计数，也不覆盖首次阅读时间。
- 管理员能查看每条公告的阅读人员及首次阅读时间。
- 公告不限定入职时间，新加入的员工也可以查看仍处于已发布状态的历史公告。
- 不要求统计固定接收人数或阅读率，也不提供评论、附件和定向发布。

### 4.5 请假申请与审批

这是本期必须完整交付的核心业务闭环。

**申请内容**

员工及部门负责人可以提交请假，内容包括：

- 请假类型：事假、病假、年假。
- 开始日期、结束日期。
- 请假天数。
- 请假原因，必填，最多 500 字。

本期统一按整天请假，日期以北京时间的自然日为准：

- 开始日期不能早于提交当天。
- 结束日期不能早于开始日期。
- 天数按首尾日期均包含的自然日计算，包括周末和节假日。
- 单次最多申请 30 天。
- 请假类型仅作分类，不管理年假余额，不要求病假证明。
- 同一申请人的待审批或已通过申请，日期区间不得重叠。
- 已驳回、已撤销的申请不占用日期区间。

**审批归属**

- 普通员工的申请，由提交时所在部门的负责人审批。
- 部门负责人的申请，由其在提交时选择的另一部门启用负责人审批。
- 不能选择自己审批。
- 没有符合条件的审批人时，禁止提交并说明原因。
- 每条申请只需要一名审批人处理，不设置多级审批。
- 提交后，申请人、提交时部门和审批人保留在历史记录中，不随后续组织调整改变。

**状态与处理规则**

| 当前状态               | 可执行操作 | 操作人       | 结果     |
| ---------------------- | ---------- | ------------ | -------- |
| 待审批                 | 通过       | 指定审批人   | 已通过   |
| 待审批                 | 驳回       | 指定审批人   | 已驳回   |
| 待审批                 | 撤销       | 申请人本人   | 已撤销   |
| 已通过、已驳回、已撤销 | 查看       | 有权查看的人 | 状态不变 |

- 提交成功后直接进入待审批状态，本期不提供申请草稿。
- 提交后不可编辑，不允许删除。
- 需要修改时，申请人先撤销待审批申请，再重新提交。
- 驳回必须填写原因；通过时审批意见可选，均最多 500 字。
- 已通过申请不支持撤销或销假；需要调整时由企业线下处理。
- 待审批申请即使已到开始日期，也不自动通过、撤销或失效，仍可处理。
- 重复提交、重复审批，或审批与撤销同时发生时，同一申请不能产生相互冲突的最终结果。

**查询与记录**

- 申请人能够查看本人的申请列表、详情、当前状态和处理意见。
- 支持按状态、请假类型及开始日期范围筛选本人申请。
- 审批人能够查看分配给自己的待审批任务和已处理记录，并按申请人姓名、状态查询。
- 详情应保留申请内容、提交时间，以及最终操作人、操作时间和意见。
- 审批人后续不再担任负责人，仍可查看自己曾处理的记录，但不能获得新的审批权限。
- 普通员工不能查看他人的请假记录。
- 负责人只能查看本人申请，以及明确分配给自己的申请，不能查看其他人的全部请假记录。
- 系统管理员没有查看请假内容或代为审批的权限。

### 4.6 工作概览

登录后的工作概览应帮助用户快速找到需要处理的事情：

- 员工：未读公告数量、本人待审批申请数量、最近申请结果。
- 部门负责人：上述信息，以及待本人审批的数量和入口。
- 系统管理员：启用员工及负责人总数、部门数量、公告草稿数量。

概览数量应与实际记录一致，并能进入对应业务。无需复杂图表、消息中心或实时推送，刷新后看到最新结果即可。

## 五、基础权限要求

- 未登录用户不能访问内部资料及业务。
- 每种角色只能执行明确授权的操作。
- 隐藏按钮不能作为唯一权限保障；即使直接发起请求，也不能越权。
- 用户不能通过修改业务编号读取他人私有信息，或审批不属于自己的申请。
- 无权访问和登录失效时，应给出明确反馈。
- 本期无需建设独立的权限配置中心或完整操作审计平台，但请假处理记录、公告发布及阅读记录必须保留。

## 六、基本非功能需求

**可用性**

- 主要面向电脑浏览器，中文界面，在常见桌面宽度下可以正常使用。
- 列表支持分页，具有空数据、加载中和加载失败反馈。
- 表单错误应指出具体问题。
- 停用账号、撤回公告、审批等重要操作应有明确确认。
- 网络失败不能显示为操作成功；用户应能够重试或查询实际结果。

**数据可靠性**

- 刷新页面或重启服务后，已成功保存的数据不丢失。
- 业务规则不能只依赖浏览器端检查。
- 失败操作不得留下半完成的业务结果。
- 历史记录应能辨认当时的申请人、所属部门及处理人，即使相关账号后来停用。

**安全与运行**

- 普通用户不能获得密码、服务端密钥或内部错误堆栈。
- 系统应保留便于排查故障的基本运行错误记录。
- 正式部署访问应使用 HTTPS。
- 面向约 50 人企业的日常使用，不要求高并发指标或性能提升承诺。

## 七、V1.0 项目边界

本期交付范围限定为：

- 账号、登录与个人资料。
- 部门、员工及负责人管理。
- 企业通讯录。
- 公告发布与阅读。
- 单级请假审批及历史查询。
- 与角色对应的工作概览。
- 必要的异常处理、基本测试和部署。

上述业务应自然形成约 10 个或以上具有独立业务价值的页面或工作界面。具体页面组织由开发负责人提出，验收以业务是否完整、操作是否合理为主，不以机械拆分页面凑数。

**本期明确不做：**

- 多企业、多租户、多层部门。
- 自定义角色、权限编辑器。
- 通用审批引擎、多级会签、转交或代理审批。
- 考勤打卡、排班、薪资、报销、采购。
- 假期余额、工作日历、半天或小时请假。
- 文件上传、附件存储、富文本编辑器。
- 即时聊天、邮件、短信、站外通知。
- AI 助手、知识库、智能审批。
- 移动端 App、小程序和专门的手机适配。
- 单点登录、第三方账号登录、自助找回密码。
- 复杂统计报表、数据导入导出。
- 高可用集群及商业级运维体系。

## 八、最终业务验收要求

验收应在实际部署环境完成，准备一个管理员、至少两个部门及各自负责人、若干普通员工和一个停用账号作为演示数据。

| 验收场景     | 通过标准                                                     |
| ------------ | ------------------------------------------------------------ |
| 入职建档     | 管理员创建员工并分配部门，员工首次登录修改密码后能使用系统   |
| 资料与通讯录 | 员工修改本人联系方式后，通讯录正确展示；不能修改他人信息     |
| 公告闭环     | 管理员发布公告，员工阅读后记为已读，管理员能查看首次阅读时间 |
| 公告撤回     | 撤回后员工无法继续查看内容，管理员仍能查询历史               |
| 请假通过     | 员工提交，指定负责人处理，员工看到已通过及完整记录           |
| 请假驳回     | 负责人填写原因后驳回，员工能查看原因并重新申请               |
| 请假撤销     | 员工撤销待审批申请，审批人不能再处理该申请                   |
| 负责人请假   | 由另一部门负责人处理，无法自行审批                           |
| 业务校验     | 非法日期、超长时长、重叠申请、缺少审批人等情况被正确阻止     |
| 防止重复处理 | 重复点击或并发操作不会产生重复有效申请或相互冲突的审批结果   |
| 权限隔离     | 员工无法读取他人请假，负责人无法审批未分配申请，管理员无法代批 |
| 组织调整     | 有待办时按规则限制调整；允许调整后，历史记录仍然准确         |
| 账号停用     | 停用账号无法登录或继续操作，相关历史记录保留                 |
| 异常与持久化 | 请求失败有反馈，刷新与重启后数据正确保留                     |
| 部署运行     | 前端、后端和数据库实际协同运行，核心流程可在浏览器完成       |

交付时还应具备：

- 实际可运行的完整项目。
- 启动、配置和部署说明。
- 基本测试记录，至少覆盖登录、权限、请假状态流转和关键异常场景。
- 已知问题与未完成项清单。

所有验收结论以实际运行和测试结果为依据；未测试、未部署或未实现的内容必须如实标明。

## 内部知识分享 V1 增量需求（计划新增）

状态：已完成（Day 8）。后端 35 项集成测试 + 前端 17 项测试全部通过，浏览器验收通过。

### 用户故事

1. 员工可以创建文章草稿，填写标题、分类、摘要和正文。
2. 员工可以在“我的文章”中查看全部状态的本人文章。
3. 员工可以修改自己的草稿或已发布文章。
4. 员工可以发布自己的草稿、撤回自己的已发布文章。
5. 员工可以浏览全部已发布文章，并按标题、分类分页检索。
6. 员工可以打开已发布文章详情；作者可以打开自己的草稿和已撤回文章。

### 状态规则

`DRAFT -> PUBLISHED -> WITHDRAWN`。草稿可编辑和发布；已发布可编辑和撤回；已撤回为第一版终态，仅作者可查看。

### 字段与校验

- 标题：去除首尾空格后 2-200 字符。
- 摘要：可选，最多 500 字符；空字符串保存为 null。
- 正文：去除首尾空格后 1-60000 字符。
- 分类：必须选择当前启用的预置分类。
- 查询：页码最小 1；每页 1-100；标题搜索最长 100 字符。

### 验收标准

覆盖完整状态流、作者归属、草稿可见性、撤回后访问、停用员工访问、搜索、分类筛选和分页；现有认证、公告、请假、部门、员工、通讯录和工作台回归通过。
