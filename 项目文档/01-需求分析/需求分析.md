# 企业 OA 系统 V1.0 需求分析总结

## 一、项目解决什么问题

为约 50 人的企业集中管理人员信息、公告和请假，解决：

- 同事信息分散，不方便查找。
- 公告容易遗漏，无法确认阅读情况。
- 请假进度不透明，历史记录不完整。
- 员工资料维护和审批处理分散。

## 二、用户角色

- **员工**：查阅通讯录和公告、维护个人联系方式、提交请假并查看结果。
- **部门负责人**：拥有员工的日常能力，同时处理分配给自己的请假申请。
- **管理员**：管理账号、部门、负责人和公告，不参与请假，也不能查看请假内容或代为审批。

每个账号只有一种角色。员工和负责人必须归属一个部门，管理员不归属部门。

## 三、业务需求

### 1. 请假业务

**员工及部门负责人：**

- 填写请假类型、开始日期、结束日期和请假原因，系统按规则计算天数。
- 类型包括事假、病假、年假。
- 查看本人申请的进度、结果及审批意见。
- 待审批申请可以撤销；填错后需要重新提交新申请，不能修改原申请。
- 所有已提交申请都不能删除。

**审批人：**

- 普通员工的申请由提交时所在部门的负责人审批。
- 负责人本人请假时，选择另一部门的启用负责人审批，不能自行审批。
- 只能处理明确分配给自己的申请。
- 可以通过或驳回；驳回必须说明原因，通过时意见可选。
- 可以查询自己的待审批任务及历史处理记录。

**关键规则：**

- 提交后进入“待审批”，之后只能变为“已通过”“已驳回”或“已撤销”，最终状态不能继续更改。
- 没有符合条件的审批人时，不能提交。
- 开始日期不能早于提交当天，结束日期不能早于开始日期。
- 按北京时间自然日计算，包含首尾日期、周末和节假日，单次最多 30 天。
- 本人待审批或已通过申请的日期不能重叠。
- 请假原因必填，最多 500 字；审批意见最多 500 字。
- 待审批申请到达请假日期后，不自动失效，仍可处理。
- 重复操作或审批与撤销同时发生时，不能产生冲突结果。
- 系统保留申请内容、提交时部门、指定审批人、提交时间、最终操作人、操作时间和意见，后续组织调整不能改变历史归属。

**业务闭环：**

员工提交 → 指定负责人审批 → 状态改变 → 员工查看结果 → 系统保留记录。

### 2. 公告业务

**员工和部门负责人：**

- 查看已发布公告，按标题搜索，区分已读与未读。
- 首次打开公告详情时记录已读和首次阅读时间。
- 重复打开不重复计数，也不覆盖首次阅读时间。
- 新员工可以查看仍处于已发布状态的历史公告。

**管理员：**

- 创建、编辑和删除公告草稿。
- 发布公告、撤回已发布公告。
- 查看阅读人员及首次阅读时间。
- 查看已撤回公告及其阅读记录。

**关键规则：**

- 公告包含标题、正文、发布人和发布时间，标题与正文必填。
- 状态包括草稿、已发布、已撤回。
- 草稿仅管理员可见。
- 已发布公告不能修改；有误时撤回，再新建公告。
- 已发布和已撤回公告不能删除。
- 撤回后，员工不能继续查看公告内容。

### 3. 账号与个人信息

**员工和部门负责人：**

- 登录、退出，查看本人资料。
- 首次登录必须修改初始密码，才能使用其他业务。
- 可以修改本人工作邮箱、联系电话和密码。
- 不能自行修改姓名、部门、角色和职务。
- 忘记密码时，由管理员重置。

**管理员：**

- 创建唯一且不可修改的登录账号，设置初始密码。
- 填写姓名、角色；员工和负责人必须指定部门，职务及联系方式可以暂缺。
- 维护人员资料，重置密码，停用账号。
- 不能停用自己的账号。

**关键规则：**

- 不开放自行注册，不删除账号。
- 密码至少 8 位，包含字母和数字，不能明文保存或在查询界面显示。
- 重置密码后，用户须重新登录并修改密码。
- 密码修改或重置后，原有登录状态失效。
- 停用账号不能登录，已登录也不能继续访问受保护业务。
- 账号停用后，历史业务记录仍保留。

### 4. 部门与员工管理

**管理员：**

- 新增部门、修改部门名称。
- 分配员工所属部门，分配或更换负责人。
- 在满足业务限制时调整人员、停用账号或删除部门。

**关键规则：**

- 部门采用单层结构，不设子部门，名称必填且唯一。
- 每个部门最多一名负责人，负责人必须是本部门的启用账号。
- 一个负责人只能负责自己所属的部门。
- 部门可以暂时没有负责人，但此时该部门员工不能提交请假。
- 更换负责人后，原负责人恢复为普通员工。
- 员工有待审批申请时，不能调部门、变更角色或停用。
- 负责人有本人待审批申请或未处理的审批任务时，不能更换、调动、变更角色或停用。
- 部门存在任何关联账号或历史申请时，不能删除。
- 不允许操作时，需要说明具体原因。

### 5. 通讯录业务

- 展示启用员工及负责人的姓名、部门、职务、工作邮箱和联系电话。
- 支持按姓名搜索、按部门筛选。
- 停用账号和独立管理账号不出现在通讯录中。
- 不公开请假记录、密码等非公开信息。
- 员工和负责人不能修改他人的通讯录资料。

### 6. 工作概览

**员工看到：**

- 未读公告数量。
- 本人待审批申请数量。
- 最近申请结果。

**部门负责人看到：**

- 员工拥有的概览信息。
- 待本人审批的数量和入口。

**管理员看到：**

- 启用员工及负责人总数。
- 部门数量。
- 公告草稿数量。

概览数量必须与实际记录一致，可以进入对应业务，刷新后获取最新结果，无需实时推送。

## 四、权限与异常要求

- 未登录不能访问内部业务。
- 员工只能查看本人请假；审批人只能查看本人申请及分配给自己的申请。
- 负责人卸任后，仍可查看自己曾处理的记录，但不能获得新的审批权限。
- 权限不能仅靠隐藏按钮，直接请求也必须受到限制。
- 表单错误、无权限、登录失效、网络失败等情况需要明确反馈。
- 请求失败不能显示成功，失败操作不能留下半完成结果。
- 列表支持分页，以及加载中、空数据和失败提示。
- 重要操作需要确认。
- 刷新页面或重启服务后，已保存数据仍然保留。



## 内部知识分享模块增量需求（已完成）

状态：已完成（Day 8）。

### 需要解决的问题

员工的操作指南、技术经验和工作复盘缺少统一沉淀入口，内容分散在聊天记录或个人文档中，难以检索和复用。

### 使用角色

- 有效员工：浏览已发布文章，按标题和分类检索；创建和管理自己的文章。
- 部门负责人：权限与员工一致，不因负责人身份获得他人文章的编辑权限。
- 管理员：第一版不参与文章创作与分类维护页面；分类通过系统预置数据维护。

### 核心规则

- 草稿和已撤回文章仅作者可见，已发布文章供全部有效员工查看。
- 作者只能修改、发布或撤回自己的文章，后端必须校验身份、账号状态、文章状态和数据归属。
- 分类第一版为系统预置、只读选择；停用分类不允许用于新文章，但历史文章仍保留分类关系。
- 不增加评论、点赞、AI 助手和跨系统统一登录。

## 知识社区增强需求分析（已完成）

围绕已发布知识文章增加单层评论、用户级点赞收藏、管理员下架复审、人工确认的 AI 写作及带真实来源的 AI 查询。员工私人草稿仍不对管理员和 AI 开放。详细角色、流程、数据边界和博客核对结论见 Day09。

**实现要点：**

- **评论**：KnowledgeComment 模型，软删除（SELF/ADMIN），管理员删除需填写原因并记录审计日志；GET/POST `/articles/:id/comments`，DELETE `/comments/:id`，DELETE `/admin/comments/:id`；内容校验 1-1000，原因校验 2-500；已删除评论显示占位，评论计数排除已删除。
- **点赞/收藏**：UNIQUE 约束 `(articleId, userId)`，PUT/DELETE 幂等；收藏列表返回 available 标记，失效收藏显示原因不返回受限内容。
- **管理员内容管理**：状态扩展 DRAFT/PUBLISHED/WITHDRAWN/TAKEN_DOWN/PENDING_REVIEW，完整审核流转；ModerationLog 记录所有操作（TAKE_DOWN/REVIEW_SUBMITTED/RESTORE_APPROVED/RESTORE_REJECTED/COMMENT_REMOVED）；管理员路由独立 ADMIN 守卫。
- **AI 辅助写作**：Provider 接口可注入，Real（DeepSeek fetch）+ Mock（测试），缺密钥返回 503 不静默降级；限流 10/min、并发 3、每日 50/用户（内存实现）；draft/rewrite/summary/query 四个端点；日志仅记录元数据。
- **AI 知识查询**：queryKnowledge 检索 PUBLISHED 文章，生成回答后 POST-VERIFY 用户+文章状态；来源由服务端从实际检索结果生成，模型无法修改。
- **安全**：Employee API 需 auth + forcePasswordChange + EMPLOYEE；Admin API 需 auth + forcePasswordChange + ADMIN；不接受客户端 authorId；文章每次操作重新检查状态；AI 提示注入防护，来源视为不可信。
