# 《企业 OA 协同办公系统 V1.0 API 设计输入文档》

## 1. 文档说明

### 1.1 文档目的

本文档用于将企业 OA 协同办公系统 V1.0 的业务需求整理为后续 RESTful API 设计的正式业务输入。

本文档明确：

- 系统身份与组织职责；
- 各模块业务操作；
- 数据访问范围；
- 权限边界；
- 查询需求；
- 状态生命周期；
- 历史记录要求；
- 重复与并发规则；
- 跨模块业务约束；
- 异常场景；
- 非功能要求；
- V1.0 功能边界；
- 后续 API 必须覆盖的业务能力。

本文档不定义：

- API URL；
- HTTP Method；
- HTTP 状态码；
- 业务错误码；
- 请求 JSON；
- 响应 JSON；
- 数据库 Schema；
- ORM 模型；
- 具体代码实现。

------

# 2. 系统范围

系统面向约 50 人的单一企业，用于集中处理：

- 企业人员与账号；
- 部门与负责人；
- 企业通讯录；
- 公司公告；
- 公告阅读情况；
- 请假申请；
- 单级请假审批；
- 工作概览。

V1.0 目标是完成企业基础 OA 业务闭环，不建设大型通用 OA 平台。

------

# 3. 身份与组织职责模型

## 3.1 基础账号角色

系统只有两种基础账号角色：

| 基础角色   | 含义       |
| ---------- | ---------- |
| `ADMIN`    | 系统管理员 |
| `EMPLOYEE` | 企业员工   |

每个账号只有一个基础角色。

系统不存在独立的 `DEPARTMENT_MANAGER` 基础角色。

------

## 3.2 系统管理员

`ADMIN`：

- 使用独立管理账号；
- 不属于任何部门；
- 负责账号管理；
- 负责部门管理；
- 负责负责人管理；
- 负责公告管理；
- 不提交请假；
- 不参与请假审批；
- 无权查看员工请假内容。

------

## 3.3 企业员工

`EMPLOYEE` 必须属于一个部门。

企业员工拥有：

- 查看企业通讯录；
- 查看公司公告；
- 维护本人允许修改的个人资料；
- 提交本人请假；
- 查询本人请假。

------

## 3.4 部门负责人

### 已确认规则

部门负责人不是独立基础账号角色，而是某个 `EMPLOYEE` 当前承担的组织职责。

即：

```
基础角色 = EMPLOYEE
+
当前承担负责人职责
=
部门负责人
```

负责人继续拥有普通员工全部能力，并额外拥有：

- 查看明确分配给自己的审批任务；
- 处理明确分配给自己的请假；
- 查看本人历史处理记录；
- 查看负责人工作概览中的审批待办信息。

### 负责人身份判断

系统必须根据当前部门负责人关系判断某员工是否承担负责人职责。

客户端不得自行声明负责人身份并以此获得权限。

### 任命负责人

任命前：

```
EMPLOYEE
```

任命后：

```
EMPLOYEE + 负责人职责
```

基础角色仍然为 `EMPLOYEE`。

### 卸任负责人

卸任后：

```
EMPLOYEE + 负责人职责
↓
EMPLOYEE
```

基础角色不发生变化。

### 负责人约束

- 每个部门最多一名负责人；
- 负责人必须属于目标部门；
- 负责人账号必须启用；
- 一名员工只能负责自己所属部门。

------

# 4. 认证与登录

## 4.1 模块目标

验证账号身份、建立和终止登录状态，并确保密码变化、账号停用以及首次登录强制修改密码能够正确限制业务访问。

## 4.2 参与角色

允许：

- `ADMIN`
- `EMPLOYEE`

负责人使用其 `EMPLOYEE` 账号登录。

------

## 4.3 登录

| 内容说明     | 业务规则                             |
| ------------ | ------------------------------------ |
| 操作名称     | 登录                                 |
| 发起角色     | 已创建账号                           |
| 操作对象     | 本人账号                             |
| 前置条件     | 账号存在并处于启用状态               |
| 输入信息     | 登录账号、密码                       |
| 字段规则     | 登录账号创建后不可修改               |
| 数据访问范围 | 本人                                 |
| 业务校验     | 账号存在、密码正确、账号启用         |
| 成功结果     | 建立有效登录状态                     |
| 失败场景     | 账号不存在、密码错误、账号停用       |
| 历史记录     | V1.0 未要求登录审计                  |
| 重复与并发   | 多设备或多次登录策略：**待产品确认** |

------

## 4.4 首次登录强制修改密码

管理员创建账号时设置初始密码。

用户首次成功认证后必须修改密码。

修改完成前禁止进入正常业务。

新密码要求：

- 至少 8 位；
- 包含字母；
- 包含数字。

**直接推导：**

强制修改密码期间允许：

- 必要身份认证；
- 修改本人密码；
- 退出登录。

禁止访问：

- 通讯录；
- 公告；
- 请假；
- 工作概览；
- 管理后台；
- 其他正常业务。

修改成功后原登录状态失效，需要重新登录。

------

## 4.5 退出登录

当前已登录用户可以退出。

成功后：

- 当前登录状态失效；
- 再次访问受保护业务必须重新认证。

------

## 4.6 修改本人密码

`ADMIN` 和 `EMPLOYEE` 均可以修改本人密码。

必须：

- 只能修改本人密码；
- 新密码满足密码规则。

成功后：

- 原登录状态失效；
- 用户需要重新登录。

------

# 5. 当前用户与个人资料

## 5.1 模块目标

让当前用户获取自己的账号、组织和个人资料，并维护允许本人修改的信息。

## 5.2 参与角色

允许：

- `ADMIN`
- `EMPLOYEE`

------

## 5.3 查看本人资料

数据范围：

> 仅本人。

资料至少包括：

- 姓名；
- 基础账号角色；
- 所属部门；
- 职务；
- 工作邮箱；
- 联系电话；
- 账号状态。

`ADMIN` 没有所属部门。

**直接推导：**

对于 `EMPLOYEE`，当前用户信息还需要能够让前端判断其是否当前承担部门负责人职责，否则前端无法正确展示负责人业务入口。

------

## 5.4 修改本人联系方式

本人允许修改：

- 工作邮箱；
- 联系电话。

禁止本人修改：

- 姓名；
- 基础角色；
- 部门；
- 职务；
- 账号状态；
- 负责人关系。

工作邮箱和联系电话的具体格式、最大长度：

**待产品确认。**

------

# 6. 账号与员工管理

## 6.1 模块目标

支持管理员完成员工入职建档、人员资料维护、部门调动、密码重置以及离职账号停用。

## 6.2 参与角色

仅：

- `ADMIN`

`EMPLOYEE` 无权管理其他账号。

负责人没有额外账号管理权限。

------

## 6.3 创建账号

| 内容说明     | 业务规则                                                     |
| ------------ | ------------------------------------------------------------ |
| 操作名称     | 创建账号                                                     |
| 发起角色     | ADMIN                                                        |
| 操作对象     | 新用户账号                                                   |
| 输入信息     | 登录账号、初始密码、姓名、基础角色、部门、职务、工作邮箱、联系电话 |
| 必填         | 登录账号、初始密码、姓名、基础角色                           |
| 数据访问范围 | 企业账号                                                     |
| 业务校验     | 登录账号全公司唯一；角色与部门关系合法                       |
| 成功结果     | 创建账号并进入首次登录强制修改密码状态                       |
| 失败场景     | 账号重复、缺少必填字段、组织关系非法                         |
| 历史记录     | 无独立审计要求                                               |
| 重复与并发   | 并发创建相同登录账号只能成功一个                             |

### 角色与部门规则

创建 `ADMIN`：

- 不分配部门。

创建 `EMPLOYEE`：

- 必须分配部门。

创建账号时不能通过独立负责人角色创建负责人。

负责人任命属于部门与负责人管理业务。

------

## 6.4 修改员工资料

管理员可以维护：

- 姓名；
- 所属部门；
- 职务；
- 工作邮箱；
- 联系电话；
- 合法业务场景下的基础账号身份。

登录账号创建后不可修改。

负责人职责不得通过修改基础 `role` 完成。

涉及部门调整时必须执行跨模块业务检查。

------

## 6.5 调动员工部门

管理员可以调整员工所属部门。

前置条件：

- 目标部门存在；
- 员工不存在本人待审批申请；
- 其他组织调整限制均满足。

如果员工当前承担负责人职责：

- 不能直接调离；
- 必须先合法更换或卸任负责人；
- 再进行部门调动。

历史请假中的提交时部门不得随本次调动改变。

------

## 6.6 重置密码

管理员可以重置其他用户密码。

成功后：

1. 原登录状态失效；
2. 用户使用重置后的密码重新登录；
3. 进入强制修改密码状态；
4. 完成修改后才能使用正常业务。

管理员能否通过账号管理功能重置自己的密码：

**待产品确认。**

------

## 6.7 停用账号

管理员可以停用其他账号。

管理员不能停用自己。

### 普通员工停用限制

存在本人待审批申请时：

> 禁止停用。

### 当前负责人停用限制

当前承担负责人职责的员工不能直接停用。

管理员必须先：

> 更换负责人或卸任负责人。

负责人更换或卸任前必须检查：

- 是否存在本人待审批申请；
- 是否存在尚未处理的审批任务。

存在任一情况：

- 禁止更换负责人；
- 禁止卸任负责人；
- 因此不能继续停用该账号。

不存在上述待办时：

1. 管理员先更换或卸任负责人；
2. 原负责人失去负责人职责；
3. 基础角色仍然为 `EMPLOYEE`；
4. 负责人关系解除；
5. 管理员才能停用该账号。

### 已确认规则

> 停用账号本身不自动解除或修改部门负责人关系。

### 停用结果

账号停用后：

- 不能再次登录；
- 已建立登录状态不能继续访问受保护业务；
- 不再出现在企业通讯录；
- 不再参与新的业务；
- 历史账号信息继续保留；
- 历史业务记录继续保留。

------

## 6.8 账号列表查询

管理员需要查询企业账号。

至少展示：

- 登录账号；
- 姓名；
- 基础角色；
- 部门；
- 职务；
- 联系方式；
- 启用状态；
- **直接推导：**是否当前承担负责人职责。

必须分页。

搜索字段：

**待产品确认。**

筛选条件：

**待产品确认。**

默认排序：

**待产品确认。**

每页默认数量：

**待产品确认。**

# 7. 部门与负责人管理

## 7.1 模块目标

维护企业单层部门结构和负责人关系，为人员组织归属和请假审批提供依据。

## 7.2 参与角色

仅：

- `ADMIN`

------

## 7.3 新增部门

输入：

- 部门名称。

规则：

- 必填；
- 公司内唯一；
- 不支持子部门；
- 创建后允许暂时没有负责人。

------

## 7.4 修改部门名称

管理员可以修改部门名称。

修改后的名称仍必须公司内唯一。

历史请假必须继续显示提交时的部门信息，不能因当前部门名称变化而改变。

------

## 7.5 删除部门

### 已确认规则

V1.0 支持删除没有任何业务关联的空部门。

管理员删除部门前必须检查：

- 是否存在关联员工；
- 是否存在当前负责人；
- 是否存在历史请假等需要保留部门历史归属的业务数据。

存在任一关联时：

> 禁止删除部门。

只有同时满足以下条件才允许删除：

- 没有关联员工；
- 没有当前负责人；
- 没有历史请假；
- 没有其他需要保留部门关联的业务数据。

删除成功后，该部门不再存在。

### V1.0 部门生命周期

V1.0 不引入部门启用、停用和恢复功能。

因此不存在：

- 停用部门；
- 恢复部门；
- 向停用部门分配员工；
- 停用部门是否参与统计等业务。

------

## 7.6 任命负责人

发起角色：

`ADMIN`

候选员工必须：

- 基础角色为 `EMPLOYEE`；
- 属于目标部门；
- 账号启用；
- 满足负责人任命业务约束。

成功后：

```
EMPLOYEE
↓
EMPLOYEE + 当前负责人职责
```

基础角色不变化。

负责人获得：

- 负责人业务入口；
- 被分配审批任务的资格；
- 负责人扩展工作概览。

------

## 7.7 更换负责人

更换前必须检查原负责人：

- 是否存在本人待审批申请；
- 是否存在尚未处理的审批任务。

存在任一情况：

> 禁止更换。

新负责人必须：

- 属于目标部门；
- 账号启用；
- 基础角色为 `EMPLOYEE`；
- 满足负责人候选条件。

成功后：

旧负责人：

```
EMPLOYEE + 负责人职责
↓
EMPLOYEE
```

新负责人：

```
EMPLOYEE
↓
EMPLOYEE + 负责人职责
```

双方基础角色均不改变。

------

## 7.8 卸任负责人

由于部门允许暂时没有负责人，因此管理员可以解除当前负责人关系而不立即指定新人。

卸任前必须检查负责人：

- 是否存在本人待审批申请；
- 是否存在尚未处理的审批任务。

存在任一情况：

> 禁止卸任。

成功后：

- 原负责人继续作为普通 `EMPLOYEE`；
- 基础角色不变；
- 不再承担负责人职责；
- 部门暂时没有负责人。

------

## 7.9 无负责人部门

部门允许暂时没有负责人。

该部门员工：

- 可以继续使用通讯录；
- 可以继续查看公告；
- 可以继续查询历史请假；

但：

> 不能提交新的请假申请。

系统必须明确提示当前部门没有可用负责人。

------

# 8. 企业通讯录

## 8.2 参与角色

- `EMPLOYEE`

只展示：

不展示：

- 停用账号；
- `ADMIN` 独立管理账号。

------

## 8.4 查询条件

明确支持：

- 姓名搜索；
- 部门筛选。

必须分页。

默认排序：

**待产品确认。**

每页数量：

**待产品确认。**

------

## 8.5 展示数据

- 姓名；
- 部门；
- 职务；
- 工作邮箱；
- 联系电话。

是否显示“部门负责人”标识：

**待产品确认。**

- 密码；
- 请假记录；
- 其他非公开业务数据。

## 8.6 权限要求

# 9. 公告管理

## 9.1 模块目标

让管理员维护企业公告，并保证正式发布内容及阅读历史可追溯。

## 9.2 参与角色

维护：

- `ADMIN`

阅读：

- 启用 `EMPLOYEE`

------

## 9.3 创建公告草稿

输入：

- 标题；
- 正文。

均必填。

正文使用纯文本。

标题最大长度：

**待产品确认。**

正文最大长度：

**待产品确认。**

初始状态：

`DRAFT / 草稿`

------

## 9.4 编辑草稿

仅 `ADMIN`。

只有 `DRAFT` 可以编辑。

------

## 9.5 删除草稿

仅 `ADMIN`。

只有 `DRAFT` 可以删除。

------

## 9.6 发布公告

合法状态流转：

```
DRAFT → PUBLISHED
```

成功后：

- 保存发布人；
- 保存发布时间；
- 全体启用 `EMPLOYEE` 可以查看。

发布后的公告禁止修改。

------

## 9.7 撤回公告

合法状态流转：

```
PUBLISHED → WITHDRAWN
```

成功后：

- 员工公告列表不再展示；
- 员工不能继续打开详情；
- 管理员仍可查询公告；
- 已有阅读记录继续保留。

撤回公告不能重新发布。

内容需要修改时：

```
撤回旧公告
↓
创建新公告
↓
重新发布
```

## 9.8 管理员公告查询

管理员可以查询：

- `DRAFT`
- `PUBLISHED`
- `WITHDRAWN`

必须分页。

搜索字段、筛选条件、默认排序：

除明确状态查询外，其余 **待产品确认**。

`PUBLISHED`

# 11. 请假申请

## 11.1 模块目标

让企业员工提交请假，并确定唯一审批人进入单级审批流程。

## 11.2 参与角色

允许：

- `EMPLOYEE`

其中：

- 普通员工按照本部门负责人规则确定审批人；
- 当前负责人按照负责人本人请假规则确定审批人。

禁止：

- `ADMIN`

------

## 11.3 申请字段

| 字段     | 规则              |
| -------- | ----------------- |
| 请假类型 | 事假、病假、年假  |
| 开始日期 | 必填              |
| 结束日期 | 必填              |
| 请假天数 | 按日期规则计算    |
| 请假原因 | 必填，最多 500 字 |

------

## 11.4 日期规则

统一按照北京时间自然日。

开始日期：

- 不得早于提交当天。

结束日期：

- 不得早于开始日期。

天数：

- 首尾日期均包含；
- 包括周末；
- 包括节假日；
- 单次最多 30 天。

V1.0：

- 不管理年假余额；
- 不要求病假证明；
- 不支持半天；
- 不支持小时请假。

------

## 11.5 日期重叠

同一申请人的：

- `PENDING`
- `APPROVED`

申请日期不得与新申请发生重叠。

以下状态不占用日期：

- `REJECTED`
- `CANCELLED`

------

## 11.6 普通员工提交

审批人为：

> 提交时本人所属部门的当前负责人。

如果部门没有负责人：

> 禁止提交。

------

## 11.7 当前负责人本人提交

负责人本质仍为 `EMPLOYEE`，因此可以提交本人请假。

但是不能自己审批自己。

负责人必须从：

> 其他部门当前处于启用状态的负责人

中选择一名审批人。

不能选择：

- 自己；
- 停用负责人；
- 不再承担负责人职责的员工。

没有合法候选审批人：

> 禁止提交。

------

## 11.8 提交结果

成功提交：

```
初始状态 = PENDING
```

V1.0：

- 不存在请假草稿；
- 提交后禁止编辑；
- 禁止删除。

需要修改申请：

```
撤销 PENDING 申请
↓
重新提交
```

------

## 11.9 历史归属

提交成功后必须固定并保留：

- 申请人；
- 必要的申请人历史信息；
- 提交时部门；
- 指定审批人。

后续：

- 员工调部门；
- 部门改名；
- 更换负责人；
- 负责人卸任；
- 账号停用；

均不能改变历史申请当时的业务归属。

------

# 13. 请假审批

## 13.1 模块目标

让当前承担负责人职责的员工处理明确分配给自己的申请，并保证申请只能产生一个最终业务结果。

## 13.2 审批资格

当前承担负责人职责的 `EMPLOYEE` 具有接收新审批任务的资格。

但负责人身份本身不能授权查看或审批全部请假。

申请级权限必须满足：

> 当前用户是该申请明确指定的审批人。

------

## 13.3 待审批查询

负责人可以查看：

> 明确分配给自己的待审批任务。

支持：

- 申请人姓名搜索；
- 状态查询。

必须分页。

默认排序：

**待产品确认。**

------

## 13.4 已处理记录

负责人可以查看：

> 自己曾经处理的申请。

负责人以后卸任：

- 仍然可以查看本人历史处理记录；
- 不会因为历史负责人身份获得新的审批任务。

------

## 13.5 通过申请

前置条件：

- 当前操作者是指定审批人；
- 申请当前仍为 `PENDING`。

审批意见：

- 可选；
- 最多 500 字。

合法流转：

```

```

必须记录：

- 最终操作人；
- 操作时间；
- 审批意见。

------

## 13.6 驳回申请

前置条件：

- 当前操作者是指定审批人；
- 申请当前仍为 `PENDING`。

驳回原因：

- 必填；
- 最多 500 字。

合法流转：

```
PENDING → REJECTED
```

必须记录：

- 最终操作人；
- 操作时间；
- 驳回原因。

# 14. 请假撤销

## 14.1 操作者

仅申请人本人。

## 14.2 前置状态

只有：

`PENDING`

允许撤销。

合法流转：

```
PENDING → CANCELLED
```

必须记录：

- 操作人；
- 操作时间。

------

## 14.3 禁止撤销

以下状态不能撤销：

- `APPROVED`
- `REJECTED`
- `CANCELLED`

已通过申请不支持销假。

需要调整时由企业线下处理。

------

# 15. 请假重复与并发

## 15.1 基本原则

同一申请只能产生一个合法最终状态。

合法最终状态：

- `APPROVED`
- `REJECTED`
- `CANCELLED`

------

## 15.2 重复操作

以下情况不得产生第二个有效业务结果：

- 重复通过；
- 重复驳回；
- 重复撤销；
- 通过后再次驳回；
- 驳回后再次通过；
- 撤销后审批；
- 审批成功后撤销。

------

## 15.3 审批与撤销并发

例如：

```
             → APPROVED
PENDING
             → CANCELLED
```

审批和撤销同时发生时：

> 只能其中一个操作成功。

**直接推导：**

先成功改变状态的操作成为最终有效结果。

其他基于旧状态的操作必须失败，并明确提示：

> 当前申请状态已经发生变化，需要重新获取最新数据。

具体事务、锁、版本控制方式由技术设计阶段决定。

# 20. 跨模块业务规则

## 20.1 用户、角色、账号状态和部门

`ADMIN`：

- 不属于部门；
- 不承担负责人职责；
- 不参与请假。

`EMPLOYEE`：

- 必须属于部门；
- 可以是普通员工；
- 可以当前承担负责人职责。

账号可以：

- 启用；
- 停用。

部门不存在启用、停用和恢复状态。

------

## 20.2 负责人任命、更换、调动、卸任与账号停用

负责人不是独立基础角色。

因此：

- 任命不改变 `EMPLOYEE` 基础角色；
- 更换不改变新旧负责人的基础角色；
- 卸任不改变 `EMPLOYEE` 基础角色；
- 负责人变化只改变当前负责人组织职责关系。

负责人存在：

- 本人待审批申请；

或者：

- 尚未处理的审批任务；

则禁止：

- 更换负责人；
- 卸任；
- 调离当前部门；
- 停用账号。

当前负责人不存在上述待办但需要停用时：

> 必须先更换或卸任负责人，再执行账号停用。

停用账号本身不自动修改负责人关系。

------

## 20.3 普通员工待审批限制

普通员工存在本人 `PENDING` 请假时禁止：

- 调部门；
- 涉及业务身份的变更；
- 停用账号。

------

## 20.4 部门删除

部门存在以下任一业务关联：

- 员工；
- 当前负责人；
- 历史请假；
- 其他必须保留的历史业务；

禁止删除。

完全没有业务关联的空部门：

> 允许删除。

V1.0 不提供部门停用和恢复。

------

## 20.5 密码与登录状态

修改密码：

```
修改成功
↓
旧登录状态失效
↓
重新登录
```

管理员重置密码：

```
重置
↓
旧登录状态失效
↓
重新登录
↓
强制修改密码
↓
正常业务
```

停用账号：

```
账号停用
↓
禁止重新登录
+
已有登录状态不能继续访问业务
```

------

## 20.6 公告发布、撤回与阅读

只有 `PUBLISHED` 公告：

- 员工可见；
- 可以产生首次阅读记录。

撤回：

- 不删除已有阅读记录；
- 员工失去查看权限；
- 管理员继续查看历史。

------

## 20.7 首次阅读

同一员工对同一公告：

- 只记录一次首次阅读；
- 重复打开不覆盖首次阅读时间；
- 不重复计数。

------

## 20.8 请假审批人确定

普通员工：

```
申请人
↓
提交时部门
↓
当前负责人
↓
固定为该申请审批人
```

当前负责人本人：

```
申请人
↓
选择其他部门当前启用负责人
↓
固定为该申请审批人
```

不能自己审批自己。

------

## 20.9 组织调整后的请假历史

请假历史必须保留提交当时：

- 申请人；
- 部门；
- 指定审批人。

员工调部门、部门改名、负责人更换、负责人卸任、账号停用均不得重写历史业务归属。

------

## 20.10 操作后的数据刷新

| 操作         | 需要反映最新结果的业务             |
| ------------ | ---------------------------------- |
| 修改联系方式 | 本人资料、通讯录                   |
| 调整部门     | 员工资料、通讯录、部门人员         |

| 更换负责人   | 部门、双方负责人能力、概览         |
| 卸任负责人   | 部门、原负责人业务入口、概览       |
| 停用员工     | 账号管理、通讯录、概览             |
| 删除空部门   | 部门列表、管理员概览               |
| 发布公告     | 公告列表、公告管理、未读数量       |
| 阅读公告     | 已读状态、未读数量、管理员阅读记录 |
| 撤回公告     | 员工公告列表、管理员公告管理       |
| 提交请假     | 本人申请、审批待办、双方概览       |
| 审批         | 申请列表、详情、审批记录、概览     |
| 撤销         | 申请列表、详情、审批待办、概览     |

V1.0 不要求实时推送。

# 21. 权限要求

## 21.1 登录要求

除登录相关业务外：

> 企业内部业务必须认证。

------

## 21.2 强制修改密码

强制修改密码未完成：

> 禁止进入正常业务。

------

## 21.3 基础角色权限

后端必须判断：

- `ADMIN`
- `EMPLOYEE`

不得信任客户端自行声明角色。

------

## 21.4 负责人职责权限

需要负责人能力的业务必须检查当前用户是否真实承担负责人职责。

但审批具体申请时还必须进一步检查：

> 当前用户是否为该申请指定审批人。

负责人身份本身不能获得查看全部请假的权限。

------

## 21.5 数据归属权限

后端必须检查：

- 当前用户；
- 基础角色；
- 账号状态；
- 当前负责人职责；
- 数据归属；
- 指定审批人；
- 当前业务状态。

------

## 21.6 防止编号越权

修改：

- 用户编号；
- 部门编号；
- 公告编号；
- 请假编号；

不能绕过业务权限。

例如：

- 普通员工不能修改请假编号查看他人申请；
- 负责人不能修改申请编号审批未分配给自己的申请；
- 员工不能通过修改用户编号修改他人资料。

前端隐藏按钮不能代替后端权限校验。

# 23. 非功能需求

## 23.1 数据持久化

成功保存的数据：

- 页面刷新后不能丢失；
- 服务重启后不能丢失。

------

## 23.2 敏感信息保护

普通用户不能获得：

- 密码；
- 服务端密钥；
- 内部错误堆栈。

------

## 23.3 密码安全

- 密码不得明文保存；
- 至少 8 位；
- 包含字母和数字；
- 修改或重置后旧登录状态失效。

------

## 23.4 统一错误反馈

业务失败必须准确反映失败原因。

不能把：

- 网络失败；
- 保存失败；
- 权限失败；
- 并发失败；

显示成业务成功。

------

## 23.5 内部错误保护

服务端内部异常：

- 不向普通用户暴露堆栈；
- 不暴露数据库、服务器等敏感内部信息。

------

## 23.6 基本运行日志

需要基本运行错误日志用于故障排查。

V1.0 不建设完整通用审计平台。

业务明确要求的：

- 公告发布信息；
- 公告阅读记录；
- 请假处理历史；

必须正常持久化。

------

## 23.7 分页

所有列表型业务必须支持分页。

默认分页大小：

**待产品确认。**

------

## 23.8 防止重复提交

重要状态变化操作不得因为：

- 重复点击；
- 请求重试；
- 并发请求；

产生多个有效业务结果。

------

## 23.9 事务和数据一致性

业务操作失败时不能留下半完成状态。

重点包括：

- 请假提交；
- 审批；
- 撤销；
- 负责人任命；
- 负责人更换；
- 负责人卸任；
- 员工调部门；
- 账号停用；
- 密码变化。

具体事务、锁和版本控制技术方案由后续技术设计决定。

------

## 23.10 时间与时区

请假日期：

> 按北京时间自然日计算。

其他业务时间，例如：

- 提交时间；
- 发布时间；
- 阅读时间；
- 审批时间；
- 撤销时间；

统一采用何种保存和展示时区：

**待产品确认。**

## 23.11 使用规模

系统面向约 50 人企业日常办公。

V1.0 不人为制定：

- 并发量；
- QPS；
- 响应时间；
- 商业级性能指标。

# 25. 已经明确的规则

以下规则已经足以作为 API 设计依据：

1. 基础账号角色只有 `ADMIN` 和 `EMPLOYEE`。
2. 不存在独立 `DEPARTMENT_MANAGER` 基础角色。
3. 部门负责人是 `EMPLOYEE` 当前承担的组织职责。
4. 管理员独立存在且不属于部门。
5. `EMPLOYEE` 必须属于部门。
6. 每个部门最多一名负责人。
7. 负责人必须是本部门启用员工。
8. 负责人拥有普通员工能力以及额外审批职责。
9. 任命、卸任负责人不改变员工基础角色。
10. 账号只能由管理员创建，不开放注册。
11. 登录账号全公司唯一且不可修改。
12. 首次登录必须修改初始密码。
13. 修改密码后原登录状态失效。
14. 管理员重置密码后原登录状态失效，并重新进入强制修改密码流程。
15. 账号通过停用处理，不删除历史账号。
16. 管理员不能停用自己。
17. 普通员工存在本人待审批申请时不能调部门或停用。
18. 当前负责人不能直接停用账号。
19. 停用当前负责人前必须先合法更换或卸任。
20. 停用账号本身不自动修改负责人关系。
21. 负责人存在本人待审批申请或未处理审批任务时禁止更换、卸任、调部门和停用。
22. 空部门允许删除。
23. 存在关联员工、负责人或历史业务的部门禁止删除。
24. V1.0 不提供部门启用、停用和恢复。
25. 通讯录只展示启用员工。
26. 公告存在 `DRAFT`、`PUBLISHED`、`WITHDRAWN` 三种状态。
27. 已发布公告不能修改或删除。
28. 已撤回公告员工不可见。
29. 撤回公告不能重新发布。
30. 公告只记录首次阅读时间。
31. 重复打开不覆盖首次阅读时间。
32. 请假按北京时间自然日计算。
33. 单次请假最多 30 天。
34. `PENDING` 和 `APPROVED` 申请不能发生日期重叠。
35. 普通员工由提交时部门当前负责人审批。
36. 当前负责人本人请假必须选择其他部门当前启用负责人。
37. 申请人不能自己审批自己。
38. 每张请假只有一名指定审批人。
39. 提交后禁止编辑和删除。
40. `PENDING` 可以通过、驳回或撤销。
41. `APPROVED`、`REJECTED`、`CANCELLED` 为最终状态。
42. 驳回必须填写原因。
43. 负责人只能审批明确分配给自己的申请。
44. 管理员不能查看员工请假或参与审批。
45. 并发审批与撤销只能产生一个最终结果。
46. 请假必须保留提交时部门和指定审批人等历史信息。
47. 组织调整不能重写历史请假归属。
48. 负责人卸任后仍可查看自己历史处理记录。
49. 工作概览根据当前业务数据生成。
50. V1.0 不要求实时推送。

# 27. 资料冲突检查

## 27.1 负责人角色问题

原始需求曾将：

- 普通员工；
- 部门负责人；
- 系统管理员；

描述为三类角色。

现已通过需求澄清正式确定：

> 基础账号角色为 `ADMIN`、`EMPLOYEE`；部门负责人属于 `EMPLOYEE` 的组织职责。

因此该冲突已经解决。

后续：

- 数据库设计；
- API 设计；
- 权限模型；
- 前端身份判断；

均应采用本次确认后的模型。

------

## 27.2 部门生命周期问题

原始需求允许没有关联账号和历史申请的空部门删除。

现已正式确认：

> V1.0 沿用该规则。

即：

- 完全无业务关联的空部门允许删除；
- 存在员工、负责人或历史业务的部门禁止删除；
- V1.0 不引入部门停用/恢复机制。

如果当前数据库设计仍存在部门 `ENABLED / DISABLED` 生命周期，则数据库设计需要调整，不能反过来覆盖本业务规则。

------

## 27.3 当前结论

当前已确认的核心业务规则之间：

> **未发现阻止 API 设计的明确冲突。**

# 28. 数据库承载检查

## 28.1 当前需要数据库能够承载

数据库需要能够支持：

- 用户账号；
- `ADMIN / EMPLOYEE` 基础角色；
- 用户所属部门；
- 当前部门负责人关系；
- 用户启用/停用；
- 强制修改密码状态；
- 登录状态失效相关机制；
- 公告；
- 公告状态；
- 公告发布信息；
- 公告首次阅读；
- 同一用户同一公告首次阅读唯一性；
- 请假申请；
- 请假类型；
- 请假日期；
- 提交时部门；
- 指定审批人；
- 必要历史快照；
- 请假状态；
- 请假处理历史；
- 最终操作人；
- 操作时间；
- 审批意见；
- 驳回原因；
- 并发状态控制所需数据；
- 停用账号后的历史关联。

------

## 28.2 需要同步调整的数据库规则

如果当前数据库设计仍存在：

> 部门 `status = ENABLED / DISABLED`

以及：

> 部门永不删除，只允许停用

则与已经确认的 V1.0 产品规则不一致。

数据库设计需要调整为能够支持：

> 完全无业务关联的空部门删除。

本文档只指出数据库承载问题，不在本阶段重新设计数据库 Schema。

------

## 28.3 历史数据要求

数据库必须保证：

- 员工调部门后，历史请假仍显示提交时部门；
- 部门改名后，历史请假不被重写；
- 更换负责人后，历史审批人不改变；
- 账号停用后，历史申请、审批和公告阅读记录仍完整；
- 负责人卸任后，历史处理记录仍可识别；
- 公告重复阅读不覆盖首次阅读时间。

# 30. 是否可以进入 API 设计阶段

## 30.1 结论

> **可以直接进入 API 设计阶段。**

## 30.2 判断依据

当前已经明确：

- 基础账号角色模型；
- 负责人组织职责模型；
- 账号生命周期；
- 当前负责人停用规则；
- 部门生命周期；
- 空部门删除规则；
- 人员调动规则；
- 公告生命周期；
- 公告阅读规则；
- 请假申请规则；
- 请假审批人确定规则；
- 请假状态机；
- 数据访问权限；
- 历史数据保留；
- 组织调整限制；
- 重复操作规则；
- 并发最终结果；
- 工作概览；
- V1.0 功能边界。

此前影响整体设计的核心问题：

1. 部门负责人是否属于独立基础角色；
2. 当前负责人如何停用；
3. 部门删除还是统一停用；

均已完成确认。

当前剩余待产品确认内容主要集中在：

- 默认排序；
- 默认分页大小；
- 部分搜索和筛选字段；
- 部分页面展示字段；
- 输入字段长度；
- 时间展示规范；
- 少量非核心权限细节。

这些问题不会阻止核心 RESTful API 的资源划分、权限模型和主要接口设计。

## 30.3 后续 API 设计约束

后续 API 设计必须同时遵守：

1. 本文档作为业务规则主要依据；
2. 最终数据库设计作为数据承载依据；
3. 数据库不能反过来修改已经确认的业务规则；
4. 如果数据库无法承载本文档中的明确业务要求，应指出数据库缺口；
5. 不得自行增加 `DEPARTMENT_MANAGER` 独立基础角色；
6. 不得自行增加部门停用/恢复；
7. 不得自行增加多级审批；
8. 不得自行扩大管理员的请假访问权限；
9. 不得因为前端隐藏按钮而省略后端权限校验；
10. 不得因为实现方便而突破 V1.0 功能边界。

## 内部知识分享 API 输入（计划新增）

状态：已完成（Day 8）。统一前缀 `/api/v1/knowledge`，仅 `ENABLED + EMPLOYEE + 已完成强制改密` 可访问。实际实现 8 个接口，DTO 使用 Zod 校验。

| 方法 | 路径 | 用途 |
|---|---|---|
